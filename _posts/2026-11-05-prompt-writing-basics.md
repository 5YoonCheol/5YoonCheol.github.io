LLM에게 뭔가를 시켜봤는데 결과가 엉뚱하게 나오면, 보통 모델 탓보다는 프롬프트에 빠진 게 있는 경우가 많다. 코드 리뷰, 쿼리 작성, 문서 정리처럼 개발하면서 자주 쓰는 작업을 기준으로, 프롬프트를 어떻게 쓰면 결과가 안정적으로 나오는지 정리해보자.

---

### 1. 프롬프트는 신입에게 업무 요청하는 메시지라고 생각하자

프롬프트를 잘 쓰는 방법을 한 줄로 줄이면 이거다. 맥락을 전혀 모르는 똑똑한 신입에게 메신저로 일을 맡긴다고 생각하면, 뭘 적어야 하는지 자연스럽게 나온다.

- 어떤 상황인지 (배경)
- 정확히 뭘 해달라는 건지 (작업)
- 결과물이 어떤 모양이어야 하는지 (형식)
- 하면 안 되는 게 뭔지 (제약)

"이 코드 좀 봐줘"라고 하면 신입도 뭘 봐야 하는지 모른다. 모델도 마찬가지다.

---

### 2. 역할보다 맥락이 먼저다

"너는 10년차 시니어 백엔드 개발자야"처럼 역할을 주는 방식이 한때 유행했는데, 역할 한 줄보다 실제 맥락이 훨씬 효과가 크다.

```text
[역할만 준 경우]
너는 시니어 백엔드 개발자야. 이 메서드를 리뷰해줘.

[맥락을 준 경우]
주문 생성 API의 서비스 메서드다. 하루 트래픽이 꽤 있어서 DB 커넥션을
오래 잡는 코드는 피하려고 한다. 트랜잭션 범위와 예외 처리 위주로 리뷰해줘.
스타일 지적은 안 해도 된다.
```

두 번째가 훨씬 쓸만한 답이 나온다. 역할은 말투를 바꾸는 정도고, 맥락은 판단 기준을 바꾼다.

---

### 3. 결과 형식을 먼저 정해두자

결과를 어디에 쓸 건지에 따라 형식을 지정하면 후처리가 거의 없어진다.

- 코드로 바로 붙여넣을 거면: "설명 없이 코드만, 언어는 Java 17"
- 문서에 넣을 거면: "마크다운 표로, 컬럼은 항목/현재/변경/이유"
- 프로그램에서 파싱할 거면: "아래 JSON 스키마에 맞춰서만 응답"

```text
다음 에러 로그를 분석해서 JSON으로만 응답해줘.
{
  "cause": "추정 원인 한 문장",
  "confidence": "high | medium | low",
  "next_steps": ["확인할 것 1", "확인할 것 2"]
}
```

형식을 정해주지 않으면 모델은 매번 다른 모양으로 답한다. 특히 코드에서 응답을 파싱할 때는 형식 지정이 필수다.

---

### 4. 예시 하나가 설명 열 줄보다 낫다

원하는 결과의 모양을 말로 길게 설명하는 것보다, 입력과 출력 예시를 한두 개 보여주는 게 낫다. 흔히 few-shot이라고 부르는 방식이다.

```text
커밋 메시지를 아래 규칙으로 만들어줘.

예시 1
변경: 로그인 실패 시 남는 로그에 사용자 ID 추가
메시지: feat(auth): 로그인 실패 로그에 사용자 ID 추가

예시 2
변경: 주문 목록 조회 시 N+1 쿼리 발생하던 문제 수정
메시지: fix(order): 주문 목록 조회 N+1 쿼리 제거

변경: 회원 탈퇴 시 쿠폰이 회수되지 않던 문제 수정
메시지:
```

예시를 줄 때 주의할 점은, 모델이 예시의 형식뿐 아니라 내용의 경향까지 따라간다는 것이다. 예시가 전부 짧으면 답도 짧게, 예시가 전부 특정 패턴이면 그 패턴만 나온다.

---

### 5. 복잡한 작업은 단계를 나누거나, 생각할 시간을 주자

한 번에 "이 요구사항 보고 설계하고 코드 짜고 테스트까지 써줘"라고 하면 중간 어딘가에서 품질이 떨어진다. 두 가지 방법이 있다.

**단계를 나눠서 여러 번 요청하기.** 먼저 설계안만 받고, 확인한 다음 구현을 시킨다. 사람과 일할 때랑 같다. 중간 결과를 검토할 수 있어서 잘못된 방향으로 끝까지 가는 걸 막는다.

**한 번에 시키되 순서를 지정하기.** 요청을 쪼개기 어렵다면 프롬프트 안에서 순서를 정해준다.

```text
다음 순서로 진행해줘.
1. 요구사항에서 모호한 부분이 있으면 먼저 질문만 하고 멈춰.
2. 모호한 부분이 없으면 변경할 파일 목록과 이유를 먼저 적어.
3. 그 다음에 코드를 작성해.
```

1번 같은 "모르면 물어보고 멈춰"가 특히 중요하다. 이게 없으면 모델은 빈칸을 멋대로 채워서 그럴듯한 결과를 만들어낸다.

---

### 6. 부정문보다 긍정문으로

"~하지 마"보다 "~해"가 더 잘 먹힌다. 부정문은 모델이 뭘 하지 말아야 하는지만 알려주고, 대신 뭘 해야 하는지는 비워둔다.

```text
[부정문]
외부 라이브러리 쓰지 마.

[긍정문]
표준 라이브러리만 사용해. 이미 프로젝트에 있는 의존성은 써도 된다.
```

제약이 꼭 필요하면 부정문을 써도 되지만, 가능하면 "대신 이렇게 해"를 같이 적어주자.

---

### 7. 모델이 모르는 걸 아는 척하지 않게 하자

LLM은 모르는 것도 자신 있게 답하는 경향이 있다. 사실 확인이 중요한 작업이면 빠져나갈 길을 만들어주자.

```text
이 라이브러리의 설정 옵션을 설명해줘.
확실하지 않은 옵션은 "확인 필요"라고 표시하고, 지어내지 마.
```

그리고 제공한 자료 안에서만 답하게 하는 것도 효과가 있다. "아래 문서에 근거해서만 답하고, 문서에 없는 내용이면 없다고 말해줘" 같은 식이다.

---

### 8. 프롬프트도 코드처럼 관리하자

같은 프롬프트를 반복해서 쓰게 되면, 그건 이미 코드다.

- 자주 쓰는 프롬프트는 파일로 저장해두고 버전 관리한다.
- 배경, 작업, 형식, 제약 블록을 나눠서 적으면 나중에 고치기 쉽다.
- 결과가 안 좋을 때 프롬프트 전체를 갈아엎지 말고, 한 군데씩 바꿔보면서 뭐가 영향을 줬는지 확인한다.
- 모델이 바뀌면 같은 프롬프트라도 결과가 달라질 수 있으니, 잘 나오던 입력/출력 몇 쌍을 테스트 케이스처럼 남겨둔다.

---

### 정리

| 원칙 | 한 줄 요약 |
|------|-----------|
| 맥락 | 역할 한 줄보다 상황 설명이 먼저 |
| 형식 | 결과를 어디에 쓸지 정하고 형식을 지정 |
| 예시 | 긴 설명보다 입력/출력 예시 한두 개 |
| 단계 | 복잡하면 쪼개거나 순서를 지정, 모르면 멈추게 |
| 표현 | 부정문보다 "대신 이렇게 해" |
| 정직 | 모르면 모른다고 하게 빠져나갈 길 만들기 |
| 관리 | 반복되는 프롬프트는 파일로, 버전 관리 |

결국 프롬프트 작성은 "요구사항을 명확하게 쓰는 일"이다. 개발자가 평소에 하던 일이라서, 익숙해지면 생각보다 금방 는다.
