> 2026년 11월에 "OAuth 2.0 이란?"과 "OAuth 1.0과 2.0의 차이" 두 글을 하나로 합치고 OAuth 2.1 내용을 더했다. 옛 주소로 들어오면 이 글로 넘어온다.
{: .prompt-info }

"구글로 로그인", "카카오로 로그인" 같은 소셜 로그인 버튼 뒤에서 돌아가는 게 OAuth 2.0이다.

OAuth 2.0은 사용자가 비밀번호를 넘겨주지 않아도 애플리케이션이 사용자 데이터에 접근할 수 있게 해주는 권한 위임(authorization) 표준이다. 사용자, 애플리케이션(클라이언트), 인증 서버, 자원 서버가 서로 주고받으면서 동작하고, 주로 API 접근 권한을 관리하는 데 쓴다. 엄밀히 말하면 "누구인지 확인"(인증)이 아니라 "무엇을 허락할지"(인가)를 다루는 프로토콜이고, 인증까지 표준화한 건 그 위에 얹은 OpenID Connect다.

---

### 등장인물 넷

**Resource Owner (자원 소유자)**
보통은 사용자다. Google Drive 파일이나 프로필처럼 자기 자원에 대한 권한을 갖고 있다.

**Client (클라이언트)**
자원 소유자가 접근을 허락한 애플리케이션이나 서비스다. 자원 서버에 사용자 데이터를 달라고 요청하는 쪽이다.

**Authorization Server (인가 서버)**
사용자를 인증하고 클라이언트에게 액세스 토큰을 발급해주는 서버다. Google의 OAuth 서버가 여기에 해당한다.

**Resource Server (자원 서버)**
클라이언트가 원하는 데이터가 실제로 있는 서버다. 인가 서버가 발급한 액세스 토큰을 확인하고 요청을 허락한다.

---

### 동작 방식 (Grant Type)

OAuth 2.0(RFC 6749)은 네 가지 승인 방식을 정의한다. 지금은 그중 둘만 권장된다.

#### 1. Authorization Code Grant (권장)

제일 많이 쓰는 방식이다. 사용자가 클라이언트에서 인가 서버로 넘어가 로그인을 마치면, 클라이언트는 인가 서버에서 Authorization Code를 받는다. 그리고 이 코드로 다시 액세스 토큰을 요청한다.

```
사용자 ──(1) 로그인 버튼──▶ 클라이언트
클라이언트 ──(2) 인가 요청(redirect)──▶ 인가 서버 ──(3) 로그인·동의──▶ 사용자
인가 서버 ──(4) code를 redirect_uri로──▶ 클라이언트
클라이언트 ──(5) code + client_secret──▶ 인가 서버 ──(6) access_token──▶ 클라이언트
클라이언트 ──(7) access_token──▶ 자원 서버
```

액세스 토큰이 사용자 쪽(브라우저)에 직접 노출되지 않아서 안전하다. 웹 애플리케이션의 기본이다.

#### 2. Client Credentials Grant (권장)

사용자를 대신하는 게 아니라 클라이언트가 자기 자격 증명으로 직접 액세스 토큰을 받는 방식이다. 서버끼리 통신하거나 백그라운드 작업을 돌릴 때 쓴다.

#### 3. Implicit Grant (폐기 예정)

코드 단계 없이 브라우저가 바로 액세스 토큰을 받는다. SPA에서 쓰던 방식인데, 토큰이 URL 조각(fragment)에 실려 브라우저 기록과 Referer에 남는다. 지금은 아래 PKCE를 붙인 Authorization Code 방식으로 대체한다.

#### 4. Resource Owner Password Credentials Grant (폐기 예정)

사용자가 클라이언트에 아이디와 비밀번호를 직접 넣고, 클라이언트가 그걸로 토큰을 받는다. 비밀번호를 클라이언트에 맡기는 거라 OAuth를 쓰는 이유 자체를 무너뜨린다. 레거시 마이그레이션 외에는 쓰지 않는다.

---

### PKCE: 공개 클라이언트를 위한 추가 장치

SPA나 모바일 앱은 `client_secret`을 숨길 곳이 없다. 그래서 Authorization Code를 가로챈 공격자가 토큰을 받아 갈 수 있다. PKCE(Proof Key for Code Exchange, RFC 7636)는 이걸 막는다.

1. 클라이언트가 임의의 `code_verifier`를 만들고, 그 해시 `code_challenge`를 인가 요청에 붙인다.
2. 토큰 요청 때 원본 `code_verifier`를 보낸다.
3. 인가 서버는 해시를 다시 계산해 일치할 때만 토큰을 준다.

code를 가로채도 `code_verifier`가 없으면 토큰을 못 받는다. 원래 공개 클라이언트용이었지만 지금은 모든 클라이언트에 쓰는 게 권장이고, OAuth 2.1에서는 필수다.

---

### 액세스 토큰과 리프레시 토큰

- Access Token: 자원 서버에 접근할 때 쓰는 토큰이다. 짧게(수 분~1시간) 만료되게 둔다. 형식은 정해져 있지 않아서 불투명 문자열일 수도, JWT일 수도 있다.
- Refresh Token: 액세스 토큰이 만료됐을 때 새 액세스 토큰을 받기 위해 쓴다. 수명이 길어서 더 조심해서 보관해야 하고, 한 번 쓰면 새 리프레시 토큰으로 바꿔 주는(rotation) 서버가 늘고 있다.

---

### OAuth 1.0과 뭐가 달라졌나

OAuth 1.0은 2007년, 2.0은 2012년에 나왔다. 둘은 호환되지 않는다.

| | OAuth 1.0 | OAuth 2.0 |
|---|---|---|
| 요청 보호 | 모든 요청에 HMAC 서명. 클라이언트 비밀 키로 서명 생성·검증 | 서명 없음. HTTPS가 필수이고 전송 보안을 TLS에 맡김 |
| 구현 난이도 | 서명 규칙(파라미터 정렬, 인코딩)이 복잡해 라이브러리 없이는 어려움 | 단순. HTTP 요청에 Bearer 토큰만 붙임 |
| 토큰 | Request Token → Access Token. 토큰 자체가 서명에 참여 | Access Token + Refresh Token. 토큰은 그냥 문자열 |
| 흐름 | 하나뿐 | 클라이언트 종류별 Grant Type |
| 모바일·SPA | 비밀 키를 숨길 수 없어 부적합 | PKCE로 대응 |

1.0은 서명 덕분에 HTTPS 없이도 요청 위변조를 막을 수 있었지만, 그 서명이 너무 복잡했다. 2.0은 보안을 TLS에 맡기고 프로토콜을 단순하게 만든 대신, 그 위에 PKCE 같은 확장을 하나씩 얹는 방식으로 발전했다. 지금 1.0을 새로 쓸 이유는 없다.

---

### OAuth 2.1: 지금까지의 모범 사례를 묶은 것

OAuth 2.1은 2.0에 쌓인 보안 권고(BCP)를 하나의 문서로 정리한 개정판이다. 새 기능을 추가하기보다 위험한 선택지를 없앴다.

- Authorization Code에는 PKCE가 필수다.
- Implicit Grant와 Password Grant는 삭제됐다.
- `redirect_uri`는 정확히 일치해야 한다. 와일드카드나 앞부분 일치는 허용하지 않는다.
- 액세스 토큰을 URL 쿼리 파라미터로 보내지 못한다. `Authorization: Bearer` 헤더로 보낸다.
- 리프레시 토큰은 한 번 쓰면 교체하거나(rotation) 특정 클라이언트에 묶어야 한다.

새로 구현한다면 2.1 기준으로 맞추면 된다. 2.0 서버와도 호환되는 부분집합이라 손해 볼 게 없다.

---

### 정리

웹 서비스 대부분이 OAuth 2.0을 쓰고 있고 소셜 로그인에서 특히 자주 본다. 직접 구현할 때 기억할 건 세 가지다. Authorization Code + PKCE를 기본으로 하고, Implicit·Password 방식은 쓰지 않으며, 액세스 토큰은 짧게 만료시키고 리프레시 토큰은 교체한다. 사용자는 편하게 로그인하고 서비스는 비밀번호를 직접 다루지 않아도 되니 양쪽 모두에게 이득인 셈이다.
