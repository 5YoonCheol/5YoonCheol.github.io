메시지 큐(Message Queue)를 쓴 비동기 아키텍처는 시스템 구성 요소들이 서로 직접 묶이지 않고 각자 일을 처리하게 만드는 구조다. 요청과 응답이 비동기로 흐르기 때문에 확장하기 쉽고, 한쪽에 문제가 생겨도 전체가 잘 버틴다. 어떤 특징이 있는지 하나씩 보자.

### 1. 비동기 처리

- 작업 요청이 큐에 쌓이고, 각 작업은 따로 처리된다.
- 클라이언트는 큐에 작업을 넣고 바로 다음 일을 하면 된다. 작업이 끝날 때까지 기다릴 필요가 없으니 처리 속도와 반응성이 좋다.

### 2. 느슨한 결합 (Loose Coupling)

- 서비스끼리 직접 통신하지 않고 큐를 거쳐 메시지를 주고받으니 서로 의존하는 정도가 줄어든다.
- 주문 시스템이라면 주문을 받는 서비스와 처리하는 서비스가 따로 돌 수 있다. 그래서 한 서비스에 장애가 나도 다른 서비스는 계속 정상 동작한다.

### 3. 확장성 (Scalability)

- 여러 소비자(Consumer)가 큐에 쌓인 메시지를 병렬로 처리할 수 있다. 부하가 커지면 소비자만 더 붙이면 되니 수평 확장이 쉽다.
- 처리할 작업이 많아지면 소비자 프로세스를 늘려서 병목을 줄이고 처리 속도를 높인다.

### 4. 신뢰성 (Reliability)

- 메시지 큐는 메시지를 안전하게 저장하고 전달해서 유실을 막는다.
- RabbitMQ나 Kafka 같은 시스템은 메시지 복제, 순서 보장, 재전송 같은 기능을 제공한다.
- 소비자가 메시지를 받아 처리하고 '확인(Acknowledgement)'을 보내야 큐에서 메시지가 지워진다. 그래서 메시지가 사라지거나 중복되지 않고 안전하게 전달된다.

### 5. 장애 격리 (Fault Isolation)

- 한 서비스의 장애가 다른 서비스로 번지지 않는다.
- 작업이 큐를 거쳐 비동기로 처리되니, 한 서비스가 잠깐 멈춰도 메시지는 큐에 쌓여 있을 뿐 다른 서비스에는 영향이 없다. 복구되면 쌓인 메시지를 차례로 처리하면 된다.

### 6. 트래픽 급증 완화 (Traffic Spike Handling)

- 갑자기 몰리는 트래픽(스파이크)을 큐가 받아주는 버퍼 역할을 한다.
- 요청이 갑자기 늘어도 일단 큐에 쌓아두고 차례대로 처리하니 과부하로 시스템이 죽는 걸 막을 수 있다.

### 7. 재시도와 지연 처리

- 특정 작업을 일정 시간 뒤에 다시 시도하거나 일부러 늦게 처리할 수 있다.
- 이메일 전송 중에 일시적인 오류가 났다면 지연 시간을 걸어서 큐에 다시 넣어두면 자동으로 재전송된다.

### 어디에 쓰나

1. 이메일/SMS 전송: 회원 가입 때 인증 이메일을 큐에 넣고 별도 전송 서버가 비동기로 보내면 가입 과정이 빨리 끝난다.
2. 주문 처리: 주문 정보를 큐에 넣고 주문 승인, 결제, 배송 처리를 비동기로 진행한다.
3. 로그 처리와 분석: 사용자 행동 데이터를 큐에 넣고 실시간 분석이나 후속 처리를 비동기로 돌려서 분석 시스템 부하를 줄인다.
4. IoT 데이터 수집: IoT 장비가 모은 데이터를 큐로 보내서 서버가 실시간으로 처리한다.
