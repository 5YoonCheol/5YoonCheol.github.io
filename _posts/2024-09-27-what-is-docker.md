### Docker란?

Docker(도커)는 애플리케이션을 컨테이너(Container)라는 단위로 묶어서 배포하고 실행할 수 있게 해주는 오픈소스 플랫폼이다. 애플리케이션을 격리된 환경인 컨테이너 안에서 돌리기 때문에, 개발자와 운영팀이 똑같은 환경에서 애플리케이션을 배포할 수 있다.

컨테이너에는 애플리케이션 코드, 런타임, 시스템 도구, 라이브러리가 전부 들어 있다. 운영체제(OS) 커널은 호스트와 공유하기 때문에 가상머신(VM)보다 훨씬 가볍고 자원도 덜 쓴다.

---

### 주요 개념

#### 이미지(Image)

애플리케이션 실행에 필요한 파일, 라이브러리, 설정을 모두 담은 변하지 않는 템플릿이다. 이미지로 컨테이너를 만들고, 여러 컨테이너가 같은 이미지를 공유할 수 있다.

이미지는 여러 레이어(layer)가 쌓인 구조라 중복 데이터가 줄고, 레이어 단위로 캐시가 돼서 빌드 시간도 짧아진다.

#### 컨테이너(Container)

이미지를 바탕으로 만든 실행 인스턴스다. 애플리케이션과 그 의존성을 담은 독립된 환경에서 돌고, 가상 머신과 달리 호스트 OS 커널을 공유해서 가볍고 빠르다.

기본적으로는 격리된 환경이지만, 필요하면 네트워크나 볼륨으로 다른 컨테이너나 호스트와 데이터를 주고받을 수 있다.

#### Dockerfile

이미지를 만드는 과정을 적은 텍스트 파일이다. 명령어 하나하나가 이미지의 레이어가 된다. 기본적인 Dockerfile은 이렇게 생겼다.

```shell
# 베이스 이미지를 지정 (예: Python)
FROM python:3.9-slim

# 애플리케이션 소스 파일 복사
COPY . /app

# 작업 디렉토리 설정
WORKDIR /app

# 의존성 설치
RUN pip install -r requirements.txt

# 컨테이너 시작 시 실행할 명령어
CMD ["python", "app.py"]
```

#### Docker 허브(Docker Hub)

Docker 이미지를 모아두는 중앙 저장소다. 공개 이미지와 개인 이미지가 엄청 많이 올라가 있고, 여기서 이미지를 받거나(pull) 내가 만든 이미지를 올릴(push) 수 있다.

예를 들어 공식 Python 이미지는 `docker pull python`으로 받으면 된다.

#### 볼륨(Volume)

컨테이너가 만들어지고 사라져도 데이터를 계속 남겨두는 방법이다. 컨테이너 안의 파일 시스템은 기본적으로 휘발성이라 컨테이너가 종료되면 데이터도 같이 사라진다. 볼륨을 쓰면 데이터를 호스트 파일 시스템에 저장하거나 다른 컨테이너와 공유할 수 있다.

#### 네트워크(Networking)

컨테이너는 기본적으로 독립된 네트워크 환경을 갖지만, 컨테이너끼리 연결할 수도 있다. 브리지, 호스트, 오버레이 같은 네트워크 모드를 지원해서 복잡한 네트워크 구성도 만들 수 있다.

---

### 어떻게 동작하나

1. 이미지 만들기
   - Dockerfile에 빌드 과정을 적고, `docker build`로 이미지를 만든다. 명령 하나가 레이어 하나로 쌓인다.
2. 컨테이너 실행
   - `docker run`으로 이미지에서 컨테이너를 띄운다. 컨테이너는 자기만의 네트워크와 파일 시스템을 갖고 실행되고, 지우면 그 환경도 같이 없어진다.
   - `docker run -d -p 8080:80 --name mycontainer nginx`
   - 위 명령은 Nginx 컨테이너를 백그라운드로 띄우고, 로컬 8080 포트를 컨테이너 80 포트에 연결한다.
3. 컨테이너 관리
   - `docker ps`: 실행 중인 컨테이너 목록을 본다.
   - `docker stop <컨테이너 이름>`: 실행 중인 컨테이너를 멈춘다.
   - `docker rm <컨테이너 이름>`: 멈춘 컨테이너를 지운다.

### 장점

1. 어디서나 똑같이 돈다
   - 애플리케이션과 의존성이 컨테이너 하나에 다 들어 있어서 개발 환경과 운영 환경이 같아진다. "개발할 땐 됐는데 운영에선 안 돼요" 같은 일이 줄어든다.
2. 가볍다
   - VM처럼 운영체제를 통째로 가상화하지 않고 호스트 커널을 공유하니 훨씬 가볍고 빨리 뜬다. 자원을 덜 써서 같은 하드웨어에 더 많은 애플리케이션을 올릴 수 있다.
3. 배포와 확장이 빠르다
   - 이미지는 빨리 빌드되고 컨테이너는 바로 실행되니 몇 초 만에 스케일 아웃할 수 있다. CI/CD 파이프라인에 붙이기도 좋고 배포와 업데이트도 쉬워진다.
4. 개발 환경을 맞추기 쉽다
   - 개발, 테스트, 운영에서 같은 이미지를 쓰니 환경 차이로 생기는 문제가 줄고 팀끼리 협업하기도 편하다.
5. 마이크로서비스와 잘 맞는다
   - 서비스마다 컨테이너를 따로 띄우면 서비스 간 의존성 문제를 격리할 수 있다.
6. 자원 격리와 보안
   - Docker는 cgroups와 네임스페이스로 프로세스마다 자원 사용을 격리한다. 애플리케이션끼리 간섭이 줄고 보안 측면에서도 낫다.

### Docker와 가상 머신의 차이

겉으로 보면 비슷해 보이지만 속은 꽤 다르다.

| 항목 | Docker(컨테이너) | 가상 머신(VM) |
| --- | --- | --- |
| 구조 | 호스트 OS의 커널을 공유하며, 애플리케이션과 라이브러리만 포함 | 독립된 운영체제(OS)를 포함한 전체 시스템 |
| 경량성 | 수 메가바이트(MB) 정도로 가볍고, 더 빠르게 실행 가능 | 수 기가바이트(GB) 용량이 필요하며, 부팅 시간이 걸림 |
| 성능 | 직접적인 하드웨어 접근과 OS 커널 공유로 높은 성능 제공 | 하이퍼바이저를 통해 간접적으로 하드웨어에 접근하여 성능 저하 가능성 있음 |
| 격리 수준 | 프로세스와 네트워크를 격리하지만, 완벽한 보안은 아님 | 완벽한 격리된 환경으로 더 높은 보안을 제공 |
| 시작 시간 | 수 초 내에 시작할 수 있음 | 수 분 정도의 시간이 소요됨 |

---

### 어디에 쓰나

1. 개발 환경 통일
   - 개발자들이 로컬에서 같은 이미지를 쓰면 "내 PC에서는 잘 됐는데..." 같은 문제가 줄어든다.
2. CI/CD 파이프라인
   - 코드를 푸시할 때마다 이미지를 만들고, 그 이미지로 빠르게 배포한다.
3. 마이크로서비스 아키텍처
   - 서비스마다 컨테이너를 나눠 띄우면 각 서비스를 따로 배포하고 관리할 수 있다.
4. 애플리케이션 샌드박싱
   - 서로 다른 애플리케이션이나 버전을 컨테이너로 격리해서 동시에 돌리거나 테스트할 수 있다.

---

이제 Docker는 컨테이너 환경의 표준처럼 쓰이고 있다. 실행 환경을 가볍고 일관되게 만들어주고, 배포와 확장도 빠르게 해준다는 게 가장 큰 이유다.
