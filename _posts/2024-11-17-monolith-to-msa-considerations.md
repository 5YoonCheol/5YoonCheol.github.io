아직 MSA를 경험해본 적도 없고 전환 작업을 해본 적도 없지만, 요새 트렌드가 MSA로 많이 넘어가는 추세인 것 같아서

모놀리식 아키텍쳐에서 MSA로 전환 시에 고려해야 할 점에 대해서 알아보았다.

기회가 된다면 전환 작업을 경험해보고 싶다!!

하나로 뭉쳐 있던 시스템을 여러 독립된 서비스로 쪼개는 일이라, 기술적으로도 조직적으로도 운영 면에서도 풀어야 할 숙제가 꽤 많을 것 같다. 하나씩 정리해보자.

---

### 1. 서비스를 어떻게 나눌까

- 도메인 경계 정하기: 비즈니스 도메인 기준으로, 각 서비스가 혼자서도 돌아갈 수 있게 나눠야 한다. `DDD(Domain-Driven Design)` 방식으로 서비스 경계를 정하는 게 좋다.
- 결합도 낮추기: 서비스끼리 의존을 최소화하고 느슨하게 연결해야 한다. DB도 공유하지 말고 서비스마다 자기 데이터를 갖게 하는 게 좋다.

### 2. 데이터 관리

- DB 분리: 모놀리식에서는 DB 하나를 같이 썼다면, MSA에서는 서비스마다 DB를 따로 둔다. 그러면 데이터 일관성 문제가 생기기 때문에 분산 트랜잭션으로 바꾸거나 `Saga Pattern` 같은 대안이 필요하다.
- 일관성: 분산 환경에서 서비스 간 데이터를 항상 딱 맞게 유지하기는 어렵다. 그래서 eventual consistency(최종 일관성) 개념을 적용하기도 한다.

### 3. 서비스 간 통신

- 통신 방식: 동기(REST API, gRPC)와 비동기(메시지 큐, 이벤트 스트리밍) 중에 고를 수 있다. 동기 방식은 호출한 쪽이 응답을 기다려야 해서 성능에 영향을 주니, 중요한 흐름은 비동기를 고려해볼 만하다.
- 네트워크 장애 대비: 서비스끼리 통신이 잦은 만큼 네트워크 장애도 생길 수 있다. `Circuit Breaker`, `Retry`, `Timeout` 같은 장치로 버틸 수 있게 해야 한다.

### 4. 트랜잭션 관리

- 분산 트랜잭션: 모놀리식에서는 트랜잭션 하나로 끝나던 작업이 MSA에서는 여러 서비스에 걸치게 된다. 일관성을 지키려면 `Saga Pattern`이나 `TCC(Try-Confirm/Cancel)` 같은 패턴을 써야 한다.
- CQRS와 이벤트 소싱: 트랜잭션이 복잡한 서비스라면 `CQRS(Command Query Responsibility Segregation)`와 이벤트 소싱으로 쓰기와 조회를 나눠서 성능을 개선할 수 있다.

### 5. 배포와 운영 환경

- 배포 자동화: 서비스마다 따로 배포할 수 있어야 한다. 그러려면 `CI/CD 파이프라인`을 갖춰야 한다.
- 컨테이너와 오케스트레이션: 서비스가 각자 돌아가니 `Docker`로 컨테이너화하고, `Kubernetes` 같은 도구로 상태를 관리하고 확장하는 게 좋다.

### 6. 모니터링과 로깅

- 분산 로깅: 서비스가 흩어져 있으니 로그도 한곳에 모아 봐야 한다. `ELK Stack(Elasticsearch, Logstash, Kibana)`이나 `Graylog`로 중앙 로깅 시스템을 만들 수 있다.
- 분산 트레이싱: 요청이 어떤 서비스들을 거쳐 갔는지 추적하려면 `Jaeger`, `Zipkin` 같은 도구가 필요하다. 느린 곳이나 장애 지점을 찾을 때 쓴다.
- 모니터링과 알림: `Prometheus`, `Grafana`로 상태를 보고, 장애가 나면 바로 알림이 오게 해둬야 한다.

### 7. 보안

- 인증과 권한: 모놀리식에서는 인증 체계 하나면 됐지만, MSA에서는 서비스마다 접근 권한을 관리해야 한다. 보통 `OAuth 2.0`이나 `JWT` 기반으로 구성한다.
- API Gateway: 외부 요청을 API Gateway 한곳에서 받아서 인증과 권한 검사를 하면 보안 관리가 수월해진다.

### 8. 조직 문화

- 팀 구조: 서비스를 독립적으로 운영하려면 팀도 거기에 맞춰야 한다. 기능별 팀이 아니라 서비스별 팀으로 바꾸는 게 좋다.
- DevOps와 자동화: 자주 배포하고 빠르게 피드백을 받으려면 DevOps 문화와 자동화된 테스트, 배포 환경이 있어야 한다.

### 9. 성능과 비용

- 네트워크 비용: 서비스 간 통신이 늘어나는 만큼 네트워크 사용량도 늘고, 성능과 비용에 영향을 준다. 통신 횟수를 줄이는 설계가 필요하다.
- 서비스별 확장: 트래픽이 몰리는 서비스만 따로 늘릴 수 있어야 한다.

---

정리해보니 MSA 전환은 기술만 바꾸는 게 아니라 조직까지 바꾸는 일이라, 전환 전에 계획과 준비를 충분히 해야겠다는 생각이 든다. 전환하고 나서도 모니터링과 운영 자동화에 계속 공을 들여야 할 것 같다.
