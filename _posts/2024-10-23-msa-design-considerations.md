MSA(Microservices Architecture)는 큰 시스템을 작고 독립적인 서비스 여러 개로 쪼개서 설계하는 방식이다.

서비스마다 따로 개발하고, 배포하고, 운영할 수 있고, 다른 서비스와는 네트워크로 통신한다. 전부 한 덩어리로 묶인 모놀리식 아키텍처보다 유연하고, 확장하거나 유지보수하기도 편하다.

### MSA를 설계할 때 고민할 것들

#### 1. 서비스를 어떤 기준으로 나눌까

제일 먼저 부딪히는 문제다. 보통은 비즈니스 도메인을 기준으로 나눈다.

전자상거래 시스템이라면 사용자 관리, 상품 관리, 주문 관리, 결제를 각각 독립된 서비스로 떼어낼 수 있다. 도메인 주도 설계(DDD, Domain-Driven Design)를 쓰면 이걸 좀 더 체계적으로 할 수 있다.

도메인을 분명하게 정의하고 그에 맞춰 서비스 경계를 그어두면, 비즈니스 로직이 바뀌어도 다른 서비스까지 흔들리는 일이 줄어든다.

#### 2. 데이터는 어떻게 나눌까

MSA에서는 서비스마다 자기 데이터를 직접 관리하니 데이터베이스도 나뉘게 된다.

DB 하나를 모든 서비스가 같이 쓰는 게 아니라, 각 서비스가 필요한 데이터만 갖고 있게 하는 게 핵심이다.

덕분에 데이터가 독립적이고 확장도 쉬워지지만, 대신 데이터 일관성 문제를 풀어야 한다. 분산 트랜잭션을 쓰는 대신 이벤트 기반 아키텍처나 사후 일관성(CQRS) 패턴을 적용해서 비동기로 일관성을 맞추는 방법이 있다.

#### 3. 서비스끼리는 어떻게 통신할까

보통 HTTP/REST, gRPC, 메시지 큐(Kafka, RabbitMQ 등)를 쓴다.

- 동기 통신: HTTP/REST나 gRPC로 서비스끼리 실시간으로 주고받는다.
- 비동기 통신: 메시지 브로커를 사이에 둔다. 주문이 끝나면 주문 서비스가 메시지를 보내고, 결제 서비스가 그걸 받아 처리하는 식이라 두 서비스가 서로 묶이지 않고 따로 돌 수 있다.

#### 4. API Gateway

작은 서비스가 여러 개 있으니, 이걸 모아서 클라이언트와 연결해줄 창구가 필요하다. 그게 API Gateway다. 클라이언트 요청을 알맞은 서비스로 보내주고, 인증, 로깅, 요청 가공 같은 일도 맡는다.

- 인증과 보안을 Gateway 한곳에서 일관되게 관리할 수 있다.
- 요청을 분산시켜 서비스 부하를 조절한다(로드 밸런싱).

#### 5. 서비스 디스커버리

서비스들이 각자 따로 실행되니, 어떤 서비스가 지금 어디서 돌고 있는지 알아야 한다. 이걸 관리하는 게 서비스 디스커버리다.

Eureka, Consul, Zookeeper 같은 도구로 서비스 위치를 동적으로 파악하고, 클라이언트가 맞는 서비스에 붙을 수 있게 해준다.

### MSA를 실제로 도입하려면

#### 1. DevOps와 CI/CD

독립적으로 배포되는 서비스가 여러 개라, CI/CD(Continuous Integration/Continuous Deployment) 파이프라인과 DevOps 문화 없이는 관리가 안 된다.

- CI/CD: 코드가 바뀌면 자동으로 빌드, 테스트, 배포까지 하는 파이프라인이다. 서비스마다 따로 배포하니 바뀐 부분만 빠르게 반영할 자동화가 꼭 있어야 한다.
- 컨테이너와 오케스트레이션: 서비스 실행 환경을 맞추고 배포를 관리하려고 Docker와 Kubernetes를 쓴다. Docker로 서비스를 컨테이너로 묶고, Kubernetes로 여러 컨테이너를 관리한다.

#### 2. 로그와 모니터링

서비스가 여러 개로 흩어져 있으니 로그와 모니터링 설계를 신경 써야 한다. 각 서비스 로그를 한곳에 모아서 같이 볼 수 있어야 하고, 서비스 상태를 지켜볼 도구도 필요하다.

ELK Stack(Elasticsearch, Logstash, Kibana)이나 Prometheus, Grafana 같은 도구로 로그와 메트릭을 관리할 수 있다.

#### 3. 트랜잭션 관리

서비스가 나뉘면 서비스 사이에 걸친 트랜잭션을 어떻게 처리할지가 골치 아파진다. 전통적인 ACID 트랜잭션은 분산 환경에서 복잡해지기 때문에 SAGA 패턴 같은 분산 트랜잭션 관리 기법을 쓴다.

SAGA 패턴은 각 서비스가 자기 로컬 트랜잭션만 처리하고, 중간에 실패하면 보상 트랜잭션을 실행해서 전체 일관성을 맞추는 방식이다.
