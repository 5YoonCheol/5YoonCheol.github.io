새 서비스를 오픈하기 전에 꼭 거쳐야 하는 게 성능 테스트다. 서버가 얼마나 버티는지, 사용자가 몰리면 어떻게 되는지, 어디서 병목이 생기는지를 미리 알아 둬야 오픈하고 나서 장애로 고생하지 않는다.

---

### 왜 하나

- 안정성 확인: 예상 트래픽에서 서버가 버티는지 보고, 갑자기 트래픽이 몰리는 상황에도 대비할 수 있다.
- 응답 속도 점검: 주요 기능이 충분히 빠르게 응답하는지 확인한다.
- 병목 찾기: 서버, DB, 네트워크 중 어디가 막히는지 찾아서 손볼 수 있다.
- 확장 계획: 예상보다 많은 부하를 걸어 보면, 사용자가 늘었을 때 언제 어떻게 늘려야 할지 계획을 세울 수 있다.

---

### 어떤 화면을 테스트해야 하나

핵심 기능을 담당하는 화면과 트래픽이 몰릴 것 같은 화면을 중심으로 잡으면 된다. 보통은 이런 화면들이 후보다.

1. 메인 화면: 대부분의 사용자가 처음 들어오는 곳이라 트래픽이 집중된다.
2. 로그인/회원가입: 인증과 DB 조회가 일어나서 부하가 걸리기 쉽다.
3. 검색/조회: DB와 붙어 있어서 데이터 처리 속도를 보기 좋다.
4. 주문/결제: 커머스라면 여기 속도가 사용자 경험에 바로 영향을 준다.
5. 대시보드/개인화 화면: 사용자마다 다른 정보를 보여줘서 서버와 DB에 부담이 간다.
6. 파일 업로드/다운로드: 파일 처리와 저장 속도를 봐야 하고, 파일이 크거나 많다면 네트워크 성능도 같이 봐야 한다.

---

### 봐야 할 지표

1. 응답 시간(Response Time): 요청에 응답하기까지 걸리는 시간. 페이지 로딩 시간이나 API 응답 속도로 잰다.
2. 처리량(Throughput): 초당 처리하는 요청 수(RPS).
3. 동시 사용자 수(Concurrent Users): 동시에 몇 명까지 받을 수 있는지. 예상 사용자 수를 감당하는지 확인할 때 중요하다.
4. TPS(Transaction Per Second): 초당 처리하는 트랜잭션 수. 결제처럼 중요한 트랜잭션 성능을 볼 때 유용하다.
5. 자원 사용률(Resource Utilization)
   - CPU: 어느 구간에서 CPU가 과부하되는지 본다.
   - 메모리: 사용량이나 메모리 누수가 없는지 본다.
   - 네트워크 대역폭: 트래픽이 늘어도 통신이 안정적인지 본다.
6. 에러율(Error Rate): 요청 중 오류가 난 비율. 예상 못 한 에러나 과부하로 생긴 문제를 찾을 수 있다.
7. 가용성(Availability): 서비스가 정상 동작한 시간. 시스템을 얼마나 믿을 수 있는지 보여준다.

---

### 테스트할 때 팁

- 시나리오는 실제 사용자가 서비스를 쓰는 흐름에 맞춰 짜야 현실적인 결과가 나온다.
- 낮은 부하, 중간 부하, 높은 부하를 다 걸어 봐야 상황별 성능을 알 수 있다.
- JMeter, Gatling, Locust 같은 도구를 쓰면 반복 테스트를 체계적으로 돌릴 수 있다.
