AI 코딩 도구를 쓰다 보면 같은 지적을 반복하게 된다. "테스트는 이 명령으로 돌려", "커밋 메시지는 한국어로", "이 디렉터리는 건드리지 마". 대화마다 다시 설명하는 건 비효율적이고, 설명을 빼먹으면 도구는 자기 방식대로 한다. 그래서 대부분의 도구가 프로젝트 안에 규칙 파일을 두는 방법을 제공한다. 어떤 파일이 있고, 거기에 뭘 적어야 효과가 있는지 정리해보자.

---

### 1. 도구별 규칙 파일

도구마다 읽는 파일 이름이 다르다. 2026년 기준으로 많이 쓰이는 것들이다.

| 도구 | 파일 | 위치 |
|------|------|------|
| Claude Code | `CLAUDE.md` | 프로젝트 루트, 하위 디렉터리, `~/.claude/` |
| GitHub Copilot | `copilot-instructions.md` | `.github/` |
| Cursor | `.cursor/rules/*.mdc` | 프로젝트 루트 |
| 공통 규약 | `AGENTS.md` | 프로젝트 루트 |

`AGENTS.md`는 특정 도구에 종속되지 않는 공통 규약으로 제안된 파일이고, 여러 도구가 이 파일을 함께 읽는다. 도구를 여러 개 쓰거나 팀원마다 쓰는 도구가 다르면 `AGENTS.md`에 공통 내용을 적고, 도구별 파일에서는 그 파일을 참조하게 하는 식으로 중복을 줄일 수 있다.

파일 이름은 바뀌기도 하고 새 도구가 계속 나오니, 쓰는 도구의 공식 문서에서 현재 이름을 확인하는 게 정확하다. 중요한 건 파일 이름보다 내용이다.

---

### 2. 규칙 파일의 역할

규칙 파일은 "이 프로젝트에 처음 온 사람에게 건네는 안내서"다. 도구는 대화가 시작될 때 이 파일을 읽고, 그 안의 내용을 기본 전제로 삼는다. 즉, 매 대화마다 자동으로 붙는 프롬프트라고 보면 된다.

그래서 두 가지 특성이 따라온다.

- 매번 읽히니까 길면 비용이 든다. 토큰을 먹고, 긴 만큼 중요한 규칙이 묻힌다.
- 코드를 보면 알 수 있는 건 적을 필요가 없다. 도구는 코드도 읽는다. 코드만 봐서는 알 수 없는 것만 적는다.

---

### 3. 뭘 적어야 하나

코드만 봐서는 알 수 없는 것들이다.

**빌드, 테스트, 실행 명령**

가장 효과가 큰 항목이다. 도구가 뭔가 고친 다음 스스로 검증하려면 어떤 명령을 쳐야 하는지 알아야 한다.

```markdown
## 명령
- 빌드: `./gradlew build`
- 테스트: `./gradlew test` (특정 클래스만: `./gradlew test --tests "클래스명"`)
- 로컬 실행: `./gradlew bootRun` (로컬 DB가 떠 있어야 한다)
- 코드 수정 후에는 반드시 테스트를 돌리고 결과를 보고한다
```

**프로젝트 구조와 각 디렉터리의 의미**

파일 트리는 도구가 볼 수 있지만, 왜 그렇게 나뉘어 있는지는 모른다.

```markdown
## 구조
- `api/`: 외부에 노출되는 컨트롤러. 비즈니스 로직을 넣지 않는다
- `domain/`: 핵심 로직. 외부 라이브러리 의존을 최소화한다
- `infra/`: DB, 외부 API 연동. domain의 인터페이스를 구현한다
- `legacy/`: 마이그레이션 중. 새 코드를 추가하지 않는다
```

**팀의 규칙**

코드 스타일 중에서 린터가 못 잡는 것, 커밋과 브랜치 규칙, 리뷰 관례 같은 것들이다.

```markdown
## 규칙
- 커밋 메시지는 한국어, 첫 줄은 50자 이내
- 브랜치는 `feature/`, `fix/`, `chore/` 접두어를 쓴다
- 예외는 삼키지 않는다. 잡았으면 로그를 남기고 다시 던진다
- 새 의존성 추가는 먼저 물어본다
```

**하지 말아야 할 것**

위험하거나 되돌리기 어려운 작업은 명시적으로 막아둔다.

```markdown
## 금지
- `main` 브랜치에 직접 푸시하지 않는다
- 마이그레이션 파일은 생성만 하고 실행하지 않는다
- `.env`, `secrets/` 아래 파일은 읽지도 수정하지도 않는다
```

**자주 하는 실수와 함정**

이 프로젝트에서 도구가 반복해서 틀리는 것들이다. 처음부터 알 수는 없고, 쓰면서 하나씩 추가하게 된다.

```markdown
## 주의
- 날짜는 모두 UTC로 저장하고 표시할 때만 변환한다
- `UserService`와 `MemberService`는 다른 개념이다. 혼용하지 않는다
- 테스트에서 실제 외부 API를 호출하지 않는다. `fake/` 아래 구현체를 쓴다
```

### 4. 적지 말아야 할 것

**코드를 보면 아는 것.** "이 프로젝트는 Spring Boot를 쓴다", "컨트롤러는 `@RestController`를 붙인다" 같은 건 도구가 파일 하나만 열어봐도 안다.

**일반적인 좋은 코드 원칙.** "가독성 좋은 코드를 작성해라", "SOLID를 지켜라"는 도구가 이미 알고 있고, 적어봐야 지시가 구체적이지 않아서 행동이 바뀌지 않는다.

**린터가 잡는 스타일.** 들여쓰기, 따옴표, 세미콜론은 린터와 포매터 설정 파일이 담당한다. 규칙 파일에는 "커밋 전에 포매터를 돌린다"만 적으면 된다.

**비밀 정보.** 규칙 파일은 보통 저장소에 커밋되고, 도구가 읽어서 외부 API로 보낸다. API 키, 내부 호스트명, 계정 정보는 절대 넣지 않는다.

---

### 5. 쓰는 방식

**명령문으로, 구체적으로.** "테스트를 잘 작성해주세요"보다 "새 public 메서드에는 단위 테스트를 추가한다"가 낫다. 도구는 모호한 표현을 자기 식으로 해석한다.

**이유를 한 줄 붙인다.** "`legacy/`에 새 코드를 추가하지 않는다 (마이그레이션 중, 곧 삭제 예정)"처럼 이유가 있으면 도구가 애매한 상황에서 규칙의 의도에 맞게 판단한다.

**짧게 유지한다.** 한 화면에 들어오는 정도가 적당하다. 길어지면 섹션별로 쪼개서 하위 디렉터리에 두거나, 별도 문서로 빼고 "필요하면 `docs/architecture.md`를 읽어라"라고 적는다. 대부분의 도구가 하위 디렉터리의 규칙 파일을 그 디렉터리 작업 때만 읽는다.

**규칙 파일도 코드 리뷰 대상이다.** 저장소에 커밋하고 PR로 바꾼다. 팀원이 각자 다른 규칙을 들고 있으면 결과물이 제각각이 된다.

---

### 6. 처음 만들 때

빈 파일에서 시작하면 뭘 적어야 할지 막막하다. 실용적인 순서는 이렇다.

1. 명령 섹션만 먼저 쓴다. 빌드, 테스트, 실행. 이것만으로도 도구가 스스로 검증을 하게 된다.
2. 도구에게 프로젝트를 둘러보고 초안을 만들어 달라고 한다. 대부분의 도구에 그런 기능이 있다. 다만 그 초안은 "코드를 보면 아는 것"으로 채워져 있을 가능성이 높으니, 4번 기준으로 절반은 지운다.
3. 쓰면서 도구가 틀릴 때마다 "주의" 섹션에 한 줄씩 추가한다. 같은 실수를 두 번 보면 규칙으로 올린다.
4. 한 달쯤 지나면 한 번 훑어보고, 더 이상 안 틀리는 항목이나 프로젝트 상황이 바뀌어 맞지 않는 항목을 지운다.

---

### 정리

| 적는다 | 적지 않는다 |
|--------|------------|
| 빌드·테스트·실행 명령 | 코드 보면 아는 기술 스택 |
| 디렉터리의 의미와 경계 | 일반적인 좋은 코드 원칙 |
| 팀 규칙, 커밋·브랜치 규약 | 린터가 잡는 스타일 |
| 금지 사항 | 비밀 정보 |
| 반복되는 실수 | |

규칙 파일은 한 번 쓰고 끝나는 게 아니라 도구와 일하면서 계속 다듬는 문서다. 도구가 틀릴 때 "이번엔 이렇게 해"라고 대화에서 고치는 대신, 규칙 파일에 한 줄 추가하는 습관이 결국 시간을 아낀다.
