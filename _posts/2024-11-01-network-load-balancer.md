### 로드 밸런서 (Load Balancer)란?

서버 한 대로 모든 요청을 받다 보면 언젠가는 버티지 못한다. 그래서 서버를 여러 대 두고 요청을 나눠 주는데, 이 나눠 주는 역할을 하는 장치나 소프트웨어가 로드 밸런서다.

트래픽을 여러 서버로 나누니 각 서버가 덜 힘들고, 응답도 빨라지고, 한 대가 죽어도 서비스가 계속 돌아간다. 요청이 들어오면 지금 가장 적당한 서버를 골라서 넘겨준다.

---

### 어떻게 동작하나

클라이언트가 요청을 보내면 로드 밸런서가 먼저 받아서 여러 서버에 고르게 나눈다. 각 서버 상태를 계속 지켜보면서, 부하가 적거나 응답이 빠른 서버로 보내는 식이다.

네트워크 계층에서 동작하느냐, 애플리케이션 계층에서 동작하느냐에 따라 L4 로드 밸런서, L7 로드 밸런서로 나뉜다.

---

### 분산 알고리즘

1. 라운드 로빈 (Round Robin): 서버에 순서대로 하나씩 돌아가며 보낸다. 단순하지만 서버 상태는 안 보기 때문에 서버끼리 성능 차이가 크면 문제가 생긴다.
2. 가중치 라운드 로빈 (Weighted Round Robin): 서버마다 가중치를 주고 가중치가 높은 서버에 더 많이 보낸다. 서버 사양이 제각각일 때 쓴다.
3. 최소 연결 (Least Connections): 지금 연결이 제일 적은 서버로 보낸다. 부하 상태에 따라 유동적으로 나눌 수 있다.
4. IP 해싱 (IP Hashing): 클라이언트 IP를 해싱해서 서버를 정한다. 같은 클라이언트는 늘 같은 서버로 가니까 상태를 유지해야 하는 서비스에 좋다.
5. 응답 시간 기반 (Response Time-Based): 서버 응답 시간을 보고 가장 빠른 서버로 보낸다.

---

### L4와 L7

OSI 7계층 중 주로 4계층이나 7계층에서 동작하고, 어디서 동작하느냐에 따라 할 수 있는 게 달라진다.

**L4 로드 밸런서 (전송 계층)**
IP 주소와 포트 번호를 보고 나눈다. TCP/UDP 수준에서 패킷을 넘겨주는 방식이라 빠르지만, 요청 내용까지는 들여다보지 못한다.

**L7 로드 밸런서 (애플리케이션 계층)**
HTTP, HTTPS 같은 애플리케이션 계층 정보를 보고 나눈다. URL, 쿠키, 헤더를 보고 판단할 수 있어서 훨씬 세밀하게 분산할 수 있다. 예를 들어 특정 URL 패턴은 A 서버로, 나머지는 B 서버로 보내는 식이다.

---

### 종류

**소프트웨어 기반**
소프트웨어로 로드 밸런싱을 한다. 설정이 쉽고 비용이 적게 들어서 유연하게 늘리기 좋다. NGINX, HAProxy, Traefik, AWS ELB(Elastic Load Balancing) 등이 있다.

**하드웨어 기반**
전용 장비로 로드 밸런싱을 한다. 대규모 트래픽을 처리할 수 있고 소프트웨어보다 성능과 안정성이 높다. F5 Networks의 BIG-IP, Citrix NetScaler 같은 장비가 있다.

**클라우드 기반**
클라우드 업체가 제공하는 로드 밸런서다. 서버를 붙이기 쉽고, 문제가 생기면 자동으로 확장해서 대응할 수 있다. AWS ALB(Application Load Balancer), GCP Cloud Load Balancing, Azure Load Balancer 등이 있다.

---

### 주요 기능

1. 트래픽 분산: 부하를 나눠서 서버가 과부하에 걸리지 않게 한다.
2. 고가용성과 장애 조치(Failover): 서버 일부가 죽어도 다른 서버로 돌려서 서비스가 멈추지 않게 한다.
3. 보안: SSL 인증서를 붙여 HTTPS를 처리하고, DDoS 공격을 어느 정도 완화할 수 있다.
4. 세션 유지(Sticky Session): 같은 클라이언트를 같은 서버로 계속 보낸다. 로그인 정보가 필요한 서비스에서 유용하다.
5. 헬스 체크: 서버 상태를 주기적으로 확인하고, 응답 없는 서버는 분배 대상에서 뺀다.

---

### 장단점

부하를 고르게 나누니 서버 성능을 제대로 쓸 수 있고 응답 시간도 줄어든다. 서버를 추가하는 것만으로 처리 능력을 늘릴 수 있고, 서버가 죽어도 서비스는 계속 돈다.

다만 신경 쓸 부분도 있다.

- 설정과 관리가 복잡하다. 특히 세션 관리와 데이터 일관성을 고민해야 한다.
- 소프트웨어든 하드웨어든 추가 비용이 든다.
- 중간에서 패킷을 한 번 더 거치니 지연 시간이 조금 늘어날 수 있다.
