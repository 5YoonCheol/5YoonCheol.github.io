> 2026년 11월에 "Load Balancer"와 "HA와 클러스터링" 두 글을 하나로 합쳐 다시 썼다. 옛 주소로 들어오면 이 글로 넘어온다.
{: .prompt-info }

서버 한 대로 모든 요청을 받다 보면 언젠가는 버티지 못하고, 그 한 대가 죽으면 서비스도 같이 멈춘다. 두 문제의 답이 같다. 서버를 여러 대 두고 앞에서 요청을 나눠 주는 것이다. 나눠 주는 장치가 로드 밸런서이고, "한 대가 죽어도 서비스가 계속되는 성질"이 고가용성(HA)이다. 둘을 같이 정리한다.

---

### 1. 로드 밸런서가 하는 일

클라이언트 요청을 먼저 받아서 뒤에 있는 서버 여러 대에 나눈다. 각 서버 상태를 계속 지켜보면서 살아 있는 서버에만 보낸다. 그래서 세 가지가 따라온다.

1. 트래픽 분산: 한 서버에 부하가 몰리지 않는다.
2. 장애 격리: 응답 없는 서버는 분배 대상에서 빠진다.
3. 수평 확장: 서버를 추가하기만 하면 처리량이 늘어난다.

그 밖에 TLS 종료(인증서를 로드 밸런서에 두고 뒤로는 HTTP), 압축, 간단한 DDoS 완화도 여기서 한다.

---

### 2. L4와 L7

OSI 계층 중 어디서 판단하느냐에 따라 할 수 있는 일이 다르다.

**L4 (전송 계층)**: IP 주소와 포트만 보고 나눈다. 패킷 내용을 열어 보지 않으니 빠르고, TCP/UDP 어떤 프로토콜이든 처리한다. DB나 gRPC 스트림처럼 HTTP가 아닌 트래픽에 쓴다. AWS NLB, HAProxy TCP 모드가 여기다.

**L7 (애플리케이션 계층)**: HTTP 요청을 열어 URL, 헤더, 쿠키를 보고 나눈다. `/api/*`는 API 서버로, `/static/*`는 정적 서버로 보내는 경로 기반 라우팅, 호스트 이름별 라우팅, 카나리 배포용 가중치 분배가 가능하다. 대신 요청을 파싱하니 L4보다 느리다. AWS ALB, NGINX, HAProxy HTTP 모드가 여기다.

웹 서비스는 보통 L7을 쓰고, 그 앞단이나 DB 앞에 L4를 둔다.

---

### 3. 분산 알고리즘

| 알고리즘 | 동작 | 맞는 상황 |
|---|---|---|
| 라운드 로빈 | 순서대로 돌아가며 | 서버 사양이 같고 요청 비용이 비슷할 때 |
| 가중치 라운드 로빈 | 가중치만큼 더 자주 | 서버 사양이 다를 때, 카나리 배포 |
| 최소 연결 | 현재 연결이 가장 적은 서버로 | 요청 처리 시간이 들쭉날쭉할 때 |
| IP 해시 | 클라이언트 IP로 서버 고정 | 같은 클라이언트를 같은 서버로 보내야 할 때 |
| 최소 응답 시간 | 가장 빨리 응답하는 서버로 | 서버 상태 차이가 클 때 |

처음에는 라운드 로빈이나 최소 연결로 시작하고, 문제가 보이면 바꾼다. IP 해시는 사무실처럼 많은 사용자가 한 IP로 나오는 환경에서 특정 서버에 몰리는 단점이 있다.

---

### 4. 헬스 체크

로드 밸런서가 "살아 있는 서버"를 판단하는 기준이다. 보통 `/health` 같은 엔드포인트를 몇 초마다 호출해서 연속 N번 실패하면 뺀다.

애플리케이션 쪽에서 신경 쓸 것이 있다.

- 헬스 체크 엔드포인트가 DB까지 확인하면, DB가 잠깐 느려질 때 모든 서버가 동시에 빠져서 전면 장애가 된다. 프로세스가 요청을 받을 수 있는지(liveness)와 트래픽을 받아도 되는지(readiness)를 나눈다.
- 배포할 때는 서버를 내리기 전에 readiness를 먼저 실패시켜 로드 밸런서에서 빠지게 하고, 진행 중인 요청이 끝날 때까지 기다린 뒤 종료한다(graceful shutdown). Spring Boot는 `server.shutdown=graceful`과 Actuator의 readiness 상태로 지원한다.

---

### 5. 세션은 어디에 두나

사용자가 서버 A에 로그인했는데 다음 요청이 서버 B로 가면, B에는 그 세션이 없다. 해결은 세 가지다.

1. 스티키 세션: 로드 밸런서가 쿠키로 같은 사용자를 같은 서버에 보낸다. 간단하지만 그 서버가 죽으면 세션도 사라지고, 부하가 고르게 나뉘지 않는다.
2. 세션 저장소 공유: 세션을 Redis 같은 외부 저장소에 둔다. 어느 서버로 가도 같은 세션을 본다. Spring Session이 이걸 해 준다.
3. 무상태(stateless): 서버에 세션을 두지 않고 JWT 같은 토큰에 필요한 정보를 담는다. 서버를 마음대로 늘리고 줄일 수 있다.

수평 확장을 전제로 하면 2번이나 3번으로 간다.

---

### 6. 고가용성(HA): 한 대가 죽어도 서비스는 산다

HA의 목표는 다운타임을 줄이는 것이다. "99.9% 가용성"이면 한 해에 약 8.7시간, "99.99%"면 약 52분까지 멈출 수 있다는 뜻이다. 이를 만드는 재료는 두 가지다.

- 이중화(redundancy): 서버, 네트워크 장비, DB를 여러 벌 둔다. 어느 한 벌이 죽어도 나머지가 서비스한다.
- 페일오버(failover): 장애가 나면 자동으로 다른 쪽으로 넘어간다. 로드 밸런서의 헬스 체크가 애플리케이션 서버의 페일오버 장치다.

애플리케이션 서버는 로드 밸런서 뒤에 두 대 이상 두면 HA가 된다. 문제는 그 뒤의 DB와 로드 밸런서 자신이다.

**DB**: 소스-레플리카 복제를 두고, 소스가 죽으면 레플리카를 승격한다. 승격을 자동화하려면 Orchestrator, MySQL InnoDB Cluster, 클라우드의 Multi-AZ 같은 장치가 필요하다. 복제 설정은 [MySQL 복제 설정으로 고가용성 확보하기](/posts/mysql-replication/)에 정리했다.

**로드 밸런서 자신**: 로드 밸런서가 한 대면 그게 단일 장애점(SPOF)이다. 직접 운영한다면 두 대를 두고 가상 IP(VIP)를 keepalived(VRRP)로 넘겨받게 구성한다. 클라우드 로드 밸런서는 이미 여러 가용 영역에 이중화돼 있어서 이 걱정을 덜어 준다.

---

### 7. 클러스터링과의 관계

클러스터링은 서버 여러 대를 하나의 그룹으로 묶어 하나의 시스템처럼 동작하게 하는 것이다. 목적은 부하 분산과 고가용성 둘 다인데, HA와 겹쳐 보여서 헷갈리기 쉽다.

- HA는 "멈추지 않는다"는 목표다. 이중화와 페일오버가 수단이다.
- 클러스터링은 "여러 대를 하나처럼 쓴다"는 구성이다. 그 결과로 HA를 얻을 수도 있고, 성능만 노릴 수도 있다.

로드 밸런서 + 애플리케이션 서버 N대는 가장 단순한 클러스터이고, 이 구성이 곧 애플리케이션 계층의 HA다. 서버끼리 상태를 공유해야 하는 클러스터(DB 클러스터, 캐시 클러스터)는 노드 간 동기화와 합의(어느 노드가 리더인가)가 추가로 필요해서 훨씬 복잡하다.

---

### 8. 비용과 트레이드오프

- 서버가 늘어나는 만큼 비용이 든다. 로드 밸런서 자체도 소프트웨어(NGINX, HAProxy)든 클라우드(ALB, NLB)든 비용이 있다.
- 요청이 한 단계를 더 거치니 지연 시간이 조금 늘어난다. L7일수록 더 그렇다.
- 상태(세션, 캐시, 로컬 파일)를 서버 밖으로 빼야 한다. 이게 가장 큰 설계 변경이다.
- 가용성 목표를 먼저 정한다. 99.9%와 99.99%는 비용이 몇 배 차이 난다.

---

### 9. 정리

로드 밸런서는 트래픽을 나누고 죽은 서버를 뺀다. 그 뒤에 서버를 두 대 이상 두면 애플리케이션 계층의 HA가 된다. 남는 단일 장애점은 DB와 로드 밸런서 자신이고, 각각 복제 + 자동 승격, 이중화 + VIP로 없앤다. 그리고 이 모든 것의 전제는 서버가 상태를 갖지 않는 것이다.
