크로스 사이트 스크립트(Cross-Site Script, XSS)는 웹 애플리케이션에서 자주 나오는 보안 취약점이다. 공격자가 웹 페이지에 악성 스크립트를 심어서, 그 페이지를 보는 다른 사용자에게 피해를 주는 공격이다.

XSS로 공격자는 사용자 세션을 가로채거나, 사용자 브라우저에서 악성 코드를 실행하거나, 사이트 자체의 신뢰를 떨어뜨릴 수 있다.

---

### 어떻게 일어나나

웹 페이지가 사용자 입력값을 제대로 검증하지 않고 그대로 화면에 그릴 때 생긴다. 공격자가 넣어 둔 스크립트가 다른 사용자의 브라우저에서 실행되는 거다. 이 스크립트로 세션 쿠키를 빼가거나, 중요한 정보를 훔치거나, 피싱 페이지로 유도하는 등 여러 방식으로 악용할 수 있다.

---

### XSS 유형

크게 세 가지로 나뉜다.

#### 1. Stored XSS (저장형)

공격자가 악성 스크립트를 웹 서버 DB에 저장해 두는 방식이다. 이후 누군가 그 페이지를 열 때마다 저장된 스크립트가 불려 와서 실행된다. 게시판, 댓글, 블로그, 사용자 프로필처럼 사용자가 쓴 내용을 저장해서 보여주는 기능에서 주로 생긴다.

예를 들어 누군가 댓글에 `<script>alert('해킹됨');</script>` 같은 코드를 써 두면, 그 댓글을 보는 모든 사용자의 브라우저에서 스크립트가 실행된다.

#### 2. Reflected XSS (반사형)

입력값을 받자마자 그대로 응답에 담아 돌려주는 곳에서 생긴다. 스크립트가 서버에 저장되지 않고, URL이나 입력값에 들어 있던 악성 코드가 서버 응답에 그대로 반사돼서 브라우저에서 실행된다.

공격자는 악성 링크를 만들어서 피해자가 클릭하도록 유도한다. 예를 들어 `https://example.com/search?q=<script>alert('해킹됨');</script>` 같은 URL을 피해자가 클릭하면, 검색 결과 페이지에서 스크립트가 실행된다.

#### 3. DOM-based XSS

클라이언트 쪽 자바스크립트가 DOM을 동적으로 바꾸는 과정에서 생긴다. 서버가 보낸 데이터가 아니라 브라우저 안에서 DOM을 조작하다가 생기는 취약점이라 서버가 개입하지 않고, 그래서 서버 로그로는 잡기 어려운 경우가 많다.

예를 들어 URL에 들어 있는 악성 입력값을 클라이언트 자바스크립트가 그대로 DOM에 넣으면서 스크립트가 실행된다.

---

### 어떤 피해가 생기나

- 세션 탈취: 세션 쿠키를 훔쳐서 그 사용자인 척 사이트에 접근한다.
- 피싱: 가짜 로그인 화면 같은 걸 띄워서 민감한 정보를 입력하게 만든다.
- 브라우저 악용: 사용자 동의 없이 브라우저 API에 접근하는 등 피해자 브라우저에서 원하는 동작을 실행한다.
- 사이트 변조: 페이지 내용을 바꾸거나 악성 링크를 끼워 넣는다.

---

### 막는 방법

결국 사용자 입력을 어떻게 다루느냐가 핵심이다.

1. 입력값 필터링: 입력값에서 HTML 태그나 자바스크립트와 관련된 위험한 문자열을 걸러낸다. 다만 필터링만으로는 완벽하지 않아서 다른 방법과 같이 써야 한다.
2. 출력할 때 인코딩(Escaping): 사용자 입력을 화면에 출력할 때 HTML 엔티티로 바꿔서 스크립트로 실행되지 않게 한다. 예를 들어 `<`와 `>`를 `&lt;`와 `&gt;`로 바꾼다.
3. CSP(Content Security Policy): 브라우저가 허용된 스크립트만 실행하도록 제한한다. 외부에서 끼워 넣은 스크립트나 인라인 스크립트 실행을 막을 수 있다.
4. HttpOnly 플래그: 세션 쿠키에 HttpOnly를 걸어 두면 자바스크립트로 쿠키에 접근할 수 없다. 세션 탈취를 막는 데 효과적이다.
5. 프레임워크 보안 기능: Django, Ruby on Rails 같은 최신 프레임워크는 XSS 방어 기능을 기본으로 제공하니 적극적으로 활용하자.
