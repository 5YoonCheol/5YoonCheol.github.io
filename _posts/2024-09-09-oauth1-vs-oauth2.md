OAuth 1.0과 OAuth 2.0은 둘 다 웹 애플리케이션과 API를 위한 인증 프레임워크다. 2.0은 1.0의 불편했던 점을 고쳐서 더 유연하고 확장하기 쉽게 다듬은 버전이다.

OAuth 2.0 자체는 이전 글 [OAuth 2.0 이란?](/posts/oauth2/)에서 다뤘으니 참고하자.

이번엔 둘의 차이를 정리해보자.

---

### 1. 간단한 역사

- OAuth 1.0: 2007년에 나왔다. 사용자가 자기 자원에 대한 접근 권한을 다른 애플리케이션에 안전하게 맡길 수 있도록 만들어졌다.
- OAuth 2.0: 2012년에 나온 후속 버전이다. 인증 방식이 더 유연해지고 구현도 쉬워졌으며, 더 다양한 상황을 지원한다.

### 2. 서명과 보안

**OAuth 1.0**은 모든 요청에 암호화 서명(Signature)을 붙여야 했다. 클라이언트 비밀 키로 서명을 만들어서 요청이 변조되지 않았음을 보장하는 방식이다. 문제는 이 서명 검증이 복잡하고 구현하기 어렵다는 것. 요청마다 서명을 해야 하니 구현이 복잡해지고, 실수 하나로 보안 구멍이 생길 수도 있었다.

**OAuth 2.0**은 서명 방식을 없애고 대신 HTTPS 통신을 필수로 했다. 보안은 HTTPS에 맡기는 거다. 서명 과정이 없으니 구현이 훨씬 단순해지고 여러 환경에서 쓰기 쉬워졌다.

### 3. 토큰 처리

**OAuth 1.0**은 Access Token과 Request Token을 명시적으로 정해서 썼다. 토큰은 보통 서명돼 있었고, 비밀 키가 들어간 복잡한 인증 과정이 필요했다.

**OAuth 2.0**은 Access Token과 Refresh Token을 도입해서 더 유연하게 다룬다. 토큰은 그냥 문자열이고, 필요하면 JWT(JSON Web Token) 같은 형식을 쓸 수도 있다. 토큰 만료와 갱신도 훨씬 쉬워졌다.

### 4. 승인 방식 (Grant Types)

**OAuth 1.0**은 인증 흐름이 하나뿐이었다. 그래서 모든 상황에 딱 맞지 않았는데, 특히 모바일이나 브라우저에서만 도는 클라이언트 앱에서 불편했다.

**OAuth 2.0**은 Authorization Code, Implicit, Resource Owner Password Credentials, Client Credentials 같은 여러 승인 방식을 제공한다. 애플리케이션 종류에 맞춰 고를 수 있어서 훨씬 유연하다.

### 5. 그 밖의 차이

- 복잡도: 1.0은 클라이언트와 서버 사이에 긴밀한 보안 관계를 요구해서 구현이 복잡했다. 2.0은 표준화된 절차 덕분에 단순해졌다.
- 확장성: 2.0이 확장성이 좋고, 상황에 맞게 커스터마이징하기도 쉽다.
- 호환성: 2.0은 1.0과 호환되지 않는다. 넘어가려면 클라이언트와 서버를 새로 구현해야 한다.

---

정리하면 OAuth 1.0은 서명 기반으로 보안을 챙겼지만 구현이 복잡하고 확장하기 어려웠다. OAuth 2.0은 보안을 HTTPS에 맡기고 구현을 단순하게 만들었고, 인증 흐름도 여러 가지를 제공한다. 그래서 지금은 대부분의 서비스가 1.0 대신 2.0을 쓴다.
