Spring Boot로 프로젝트를 만들면 DB 커넥션 풀은 알아서 붙는다. 기본값은 HikariCP고, 설정을 하나도 안 건드려도 돌아간다. 그래서 대부분 트래픽이 늘어나 "커넥션을 못 얻어서 타임아웃"이 나기 시작할 때 처음 들여다본다. 그때 가서 숫자를 막 올리면 또 다른 문제가 생긴다. 커넥션 풀이 왜 있는지부터, 몇 개로 잡아야 하는지, 꼭 봐야 할 설정이 뭔지 정리해보자.

---

### 1. 커넥션 풀이 하는 일

DB 커넥션을 맺는 건 비싼 작업이다. TCP 연결, 인증, 세션 초기화까지 거치면 쿼리 한 번보다 오래 걸리는 경우가 많다. 요청마다 커넥션을 새로 맺고 끊으면 DB와 애플리케이션 모두 그 비용을 매번 치른다.

커넥션 풀은 미리 커넥션을 몇 개 맺어두고 빌려주는 방식이다. 요청이 오면 풀에서 하나 꺼내 쓰고, 끝나면 반납한다. 끊는 게 아니라 돌려놓는 것이다.

```text
요청 A ─┐                 ┌─ 커넥션 1 ─┐
요청 B ─┼─ 풀에서 빌림 ──┼─ 커넥션 2 ─┼── DB
요청 C ─┘                 └─ 커넥션 3 ─┘
요청 D ─── 대기 (풀이 비었음, connectionTimeout까지 기다림)
```

풀이 비어 있으면 요청은 기다린다. 이 대기가 길어지면 응답이 느려지고, 정해진 시간을 넘기면 예외가 난다. "커넥션 풀 문제"는 대개 이 대기에서 나타난다.

---

### 2. 커넥션은 많을수록 좋은 게 아니다

직관적으로는 커넥션이 많으면 대기가 줄어들 것 같다. 그런데 DB 입장에서 보면 다르다.

DB 서버의 CPU 코어는 한정돼 있다. 코어가 4개인데 커넥션 100개가 동시에 쿼리를 던지면, DB는 100개를 번갈아 처리하느라 컨텍스트 스위칭 비용을 치른다. 디스크 I/O도 마찬가지다. 동시에 처리할 수 있는 양을 넘어서면 커넥션을 늘려도 전체 처리량은 늘지 않고 오히려 줄어든다.

HikariCP 문서에서 제시하는 출발점은 이렇다.

```text
커넥션 수 = (CPU 코어 수 × 2) + 디스크 수
```

DB 서버 코어가 4개, SSD 하나면 10개 안쪽에서 시작하라는 얘기다. 숫자가 작아 보이지만, 커넥션 하나가 쿼리 하나를 몇 ms 안에 처리하고 반납하면 10개로도 초당 수천 건을 소화한다. 이 공식은 쿼리가 짧고 CPU 위주일 때의 기준이고, 느린 쿼리나 외부 I/O를 기다리는 트랜잭션이 섞여 있으면 조금 더 필요하다.

실제로는 이 값을 출발점으로 두고, 부하 테스트에서 풀 대기 시간과 DB CPU 사용률을 같이 보면서 조정한다. 대기가 길어지는데 DB CPU가 놀고 있으면 늘리고, DB CPU가 이미 꽉 찼으면 늘려도 소용없다. 그때는 쿼리를 고치는 게 답이다.

---

### 3. 애플리케이션 인스턴스가 여러 개라면

커넥션 수는 애플리케이션 인스턴스마다 따로 잡힌다. 인스턴스 하나에 풀 20개를 잡고 서버를 5대 띄우면 DB에는 커넥션 100개가 붙는다. 여기에 배치 서버, 관리자 도구, 모니터링까지 붙으면 더 늘어난다.

그래서 풀 크기를 정할 때는 "DB가 감당할 총 커넥션 수"를 먼저 정하고, 그걸 인스턴스 수로 나눠야 한다. MySQL이면 `max_connections` 설정이 상한인데, 이 상한에 가까워지면 새 커넥션 자체가 거부된다. 애플리케이션을 스케일 아웃할 때 DB 커넥션 수를 같이 계산하지 않으면 서버를 늘렸는데 더 느려지는 일이 생긴다.

---

### 4. 봐야 할 설정

Spring Boot에서는 `spring.datasource.hikari.*` 아래에 둔다.

```yaml
spring:
  datasource:
    hikari:
      maximum-pool-size: 10
      minimum-idle: 10
      connection-timeout: 3000
      max-lifetime: 1500000
      idle-timeout: 600000
      leak-detection-threshold: 10000
```

하나씩 보자.

**maximum-pool-size** (기본 10)
풀이 가질 수 있는 최대 커넥션 수. 위에서 다룬 그 숫자다.

**minimum-idle** (기본은 maximum-pool-size와 같음)
놀고 있을 때 유지하는 최소 커넥션 수. HikariCP는 이 값을 최대와 같게 두는 걸 권장한다. 고정 크기 풀이 되어서 트래픽이 갑자기 몰릴 때 커넥션을 새로 맺느라 느려지는 일이 없다. 줄여서 얻는 건 DB 메모리 약간인데, 그걸 아껴야 하는 상황은 드물다.

**connection-timeout** (기본 30000ms)
풀에서 커넥션을 얻기까지 기다리는 최대 시간. 기본 30초는 너무 길다. 사용자 요청이 30초를 기다리게 두는 것보다 빨리 실패하고 에러를 돌려주는 게 낫다. 몇 초 안쪽으로 줄이는 게 보통이다. 다만 이걸 줄이면 풀 부족이 타임아웃 예외로 더 자주 드러나는데, 그건 문제를 숨기지 않고 보여주는 것이니 나쁜 게 아니다.

**max-lifetime** (기본 1800000ms, 30분)
커넥션 하나를 최대 얼마나 쓰고 버릴지. 이 설정이 중요한 이유는 DB 쪽에도 유휴 커넥션을 끊는 설정이 있어서다. MySQL은 `wait_timeout`(기본 8시간)이 지나면 커넥션을 서버 쪽에서 끊는다. HikariCP의 max-lifetime이 그보다 길면, 풀은 살아 있다고 믿는 커넥션이 실제로는 끊어진 상태가 되고, 꺼내 쓰는 순간 에러가 난다. 그래서 max-lifetime은 DB의 유휴 타임아웃보다 몇 초에서 몇 분 짧게 잡는다. 중간에 로드밸런서나 프록시가 있으면 그쪽 타임아웃도 봐야 한다. 클라우드 환경에서 "한참 놀다가 첫 요청이 실패한다"는 증상의 대부분이 이 불일치다.

**idle-timeout** (기본 600000ms, 10분)
minimum-idle보다 많은 유휴 커넥션을 얼마나 두고 정리할지. minimum-idle을 maximum-pool-size와 같게 두면 정리할 유휴 커넥션이 없으니 이 설정은 사실상 안 쓰인다.

**leak-detection-threshold** (기본 0, 꺼짐)
커넥션을 빌려가고 이 시간 안에 반납하지 않으면 경고 로그를 남긴다. 기본은 꺼져 있다. 개발과 스테이징에서는 켜두는 게 좋다. 커넥션을 반납하지 않는 코드(트랜잭션 안에서 외부 API를 오래 기다리는 코드, 예외 경로에서 close가 빠진 코드)를 잡아준다. 최솟값은 2초고, 정상적인 트랜잭션보다 충분히 긴 값으로 둔다.

---

### 5. 풀을 오래 잡고 있는 코드

풀 크기를 아무리 잘 잡아도, 커넥션 하나를 오래 붙들고 있는 코드가 있으면 풀은 금방 바닥난다. 자주 보이는 패턴이다.

**트랜잭션 안에서 외부 호출.** `@Transactional` 메서드 안에서 결제 API나 메일 발송처럼 수 초가 걸릴 수 있는 호출을 하면, 그 시간 동안 커넥션은 묶여 있다. 외부 호출을 트랜잭션 밖으로 빼거나, 트랜잭션 범위를 DB 작업에만 좁힌다.

**컨트롤러 전체에 트랜잭션.** 요청 처리 전체를 트랜잭션으로 감싸면 뷰 렌더링이나 응답 직렬화까지 커넥션을 잡는다. 트랜잭션은 서비스 계층의 DB 작업 단위에만 건다.

**OSIV(Open Session In View).** Spring Boot는 JPA를 쓸 때 기본으로 OSIV가 켜져 있어서 요청이 끝날 때까지 영속성 컨텍스트가, 경우에 따라 커넥션이 유지된다. 트래픽이 많은 API 서버라면 `spring.jpa.open-in-view=false`로 끄고 지연 로딩을 서비스 계층에서 끝내는 쪽이 커넥션 회전이 빠르다.

**REQUIRES_NEW 남용.** 새 트랜잭션을 열면 커넥션을 하나 더 빌린다. 바깥 트랜잭션이 커넥션을 잡고 있는 상태에서 안쪽이 또 빌리니, 풀이 작으면 서로 기다리다 데드락처럼 멈추는 일도 생긴다.

---

### 6. 문제가 났을 때 보는 것

"커넥션을 얻지 못함" 예외가 나면 순서대로 확인한다.

1. 풀 메트릭. Actuator를 쓰면 `hikaricp.connections.active`, `pending`, `timeout` 같은 지표가 나온다. active가 maximum에 붙어 있고 pending이 쌓이면 풀이 부족한 게 맞다.
2. 느린 쿼리. 풀이 부족한 원인이 쿼리가 느려서 커넥션 회전이 안 되는 것일 수 있다. 슬로우 쿼리 로그를 켜서 본다. 이 경우 풀을 늘리는 건 증상만 가린다.
3. 커넥션을 오래 잡는 코드. leak-detection-threshold를 켜고 어느 스택에서 경고가 나는지 본다.
4. DB 쪽 상태. DB CPU가 이미 꽉 차 있으면 애플리케이션 쪽에서 할 수 있는 건 쿼리 개선이다.

풀 크기를 올리는 건 이 네 가지를 확인한 다음 마지막에 하는 일이다.

### 정리

| 설정 | 요령 |
|------|------|
| maximum-pool-size | 코어×2+디스크에서 시작, 부하 테스트로 조정. 인스턴스 수를 곱해서 DB 상한과 비교 |
| minimum-idle | maximum과 같게 (고정 풀) |
| connection-timeout | 기본 30초는 길다. 몇 초로 |
| max-lifetime | DB와 프록시의 유휴 타임아웃보다 짧게 |
| leak-detection-threshold | 개발·스테이징에서 켜두기 |

커넥션 풀은 숫자 하나 바꾸는 설정이 아니라 DB 용량, 인스턴스 수, 트랜잭션 범위가 다 얽힌 문제다. 풀이 부족해 보일 때 숫자를 올리기 전에, 커넥션을 누가 오래 잡고 있는지 먼저 보는 습관이 결국 시간을 아낀다.
