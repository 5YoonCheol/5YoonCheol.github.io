LLM은 그 자체로는 텍스트를 받아 텍스트를 내놓는 것밖에 못 한다. DB를 조회하거나 API를 호출하거나 파일을 고치려면 누군가 그 일을 대신 해줘야 하는데, 그게 도구(tool)다. 에이전트를 만든다는 건 결국 모델에게 어떤 도구를 어떻게 설명해서 쥐어주느냐의 문제다. 도구 정의를 어떻게 쓰느냐에 따라 같은 모델이 똑똑해 보이기도 하고 멍청해 보이기도 한다. 도구 정의의 구조와, 잘 쓰는 요령을 정리해보자.

---

### 1. 도구 호출이 돌아가는 방식

먼저 흐름을 알아야 한다. 모델이 직접 뭔가를 실행하는 게 아니다.

```text
1. 개발자: 모델에게 "이런 도구들이 있다"고 목록(이름, 설명, 파라미터 스키마)을 넘긴다
2. 사용자: "서울 내일 날씨 알려줘"
3. 모델: "get_weather 도구를 city=서울, date=내일로 호출하고 싶다"는 구조화된 응답을 낸다
4. 개발자 코드: 실제로 get_weather 함수를 실행해서 결과를 얻는다
5. 개발자 코드: 그 결과를 모델에게 다시 넘긴다
6. 모델: 결과를 보고 사용자에게 답한다 (또는 다른 도구를 또 호출한다)
```

핵심은 3번과 4번 사이다. 모델은 "이 도구를 이 인자로 부르겠다"고 말할 뿐이고, 실행은 내 코드가 한다. 그래서 모델이 엉뚱한 도구를 고르거나 인자를 틀리게 넣으면, 그건 대부분 1번에서 넘긴 도구 설명이 부족했기 때문이다.

이 방식을 function calling이라고도 부르고, 도구 정의와 호출 방식을 표준화한 프로토콜로 MCP(Model Context Protocol)가 있다. 어느 쪽이든 도구를 정의하는 요소는 같다.

---

### 2. 도구 정의의 세 요소

도구 하나는 이름, 설명, 입력 스키마로 이루어진다.

```json
{
  "name": "search_orders",
  "description": "주문을 조건으로 검색한다. 고객 이름, 기간, 상태로 필터링할 수 있다. 최대 50건까지 반환하며, 더 많으면 next_cursor가 함께 온다. 주문 1건의 상세 정보가 필요하면 get_order를 대신 사용한다.",
  "input_schema": {
    "type": "object",
    "properties": {
      "customer_name": {
        "type": "string",
        "description": "고객 이름. 부분 일치로 검색한다."
      },
      "status": {
        "type": "string",
        "enum": ["pending", "paid", "shipped", "cancelled"],
        "description": "주문 상태. 생략하면 전체."
      },
      "from_date": {
        "type": "string",
        "description": "검색 시작일, YYYY-MM-DD 형식. 생략하면 30일 전."
      },
      "to_date": {
        "type": "string",
        "description": "검색 종료일, YYYY-MM-DD 형식. 생략하면 오늘."
      }
    },
    "required": []
  }
}
```

모델은 이 JSON만 보고 언제 이 도구를 쓸지, 인자를 어떻게 채울지 결정한다. 그래서 이 JSON은 코드가 아니라 모델을 위한 문서다.

---

### 3. 이름

동사로 시작하고, 무엇을 대상으로 하는지 드러나게 짓는다. `search_orders`, `get_order`, `cancel_order`처럼.

피해야 할 이름은 두 종류다. `process`, `handle`, `execute`처럼 뭘 하는지 모를 이름, 그리고 `tool1`, `api_call`처럼 구분이 안 되는 이름. 모델은 이름을 가장 먼저 보고 후보를 추린다.

도구가 많아지면 접두어로 묶는다. `db_query`, `db_insert`, `file_read`, `file_write`처럼 같은 영역의 도구에 같은 접두어를 붙이면 모델이 "파일 관련 작업이면 file_ 중에서 고르면 된다"고 판단한다.

---

### 4. 설명

가장 중요한 부분이다. 함수 주석을 쓰듯 "주문을 검색한다" 한 줄로 끝내면 모델도 그 정도만 안다. 좋은 설명에는 네 가지가 들어간다.

**무엇을 하는가.** 한 문장으로.

**언제 써야 하고, 언제 쓰지 말아야 하는가.** 비슷한 도구가 여럿일 때 모델이 가장 많이 틀리는 부분이다. "1건 상세는 get_order를 쓴다"처럼 다른 도구로 가는 길을 설명 안에 적어두면 혼동이 크게 줄어든다.

**결과가 어떤 모양인가.** "최대 50건, 더 있으면 next_cursor"처럼 결과의 한계와 형태를 알려주면 모델이 결과를 받고 다음 행동을 제대로 한다. 안 적어두면 50건이 전부인 줄 알고 "총 50건입니다"라고 답한다.

**부작용이 있는가.** 조회인지 변경인지, 되돌릴 수 있는지. "이 작업은 취소할 수 없다"고 적어두면 모델이 호출 전에 사용자에게 확인하는 쪽으로 행동한다.

```text
[나쁜 설명]
주문을 삭제한다.

[좋은 설명]
주문을 영구 삭제한다. 되돌릴 수 없으므로 사용자가 명시적으로 삭제를 요청한 경우에만
사용한다. 주문을 취소 상태로 바꾸는 것이 목적이면 cancel_order를 대신 사용한다.
배송이 시작된 주문은 삭제할 수 없고 에러를 반환한다.
```

설명이 길어지는 걸 겁내지 않아도 된다. 도구 설명은 사람이 읽을 API 문서가 아니라 모델이 판단 근거로 쓰는 텍스트다. 서너 문장에서 한 단락 정도가 보통이다.

---

### 5. 파라미터

**파라미터마다 설명을 붙인다.** 타입만 있고 설명이 없으면 모델은 이름으로 추측한다. `date`가 어느 형식인지, `limit`의 최대가 얼마인지, 생략하면 어떻게 되는지를 적는다.

**enum을 적극적으로 쓴다.** 값이 정해져 있으면 enum으로 묶는다. "status는 pending, paid, shipped 중 하나"라고 설명에만 적는 것보다, 스키마의 enum으로 넣는 게 모델이 틀릴 여지를 없앤다.

**파라미터를 줄인다.** 파라미터가 열 개 넘는 도구는 모델이 채우다가 틀린다. 꼭 필요한 것만 남기고, 나머지는 기본값을 두거나 도구를 쪼갠다.

**모델이 알 수 없는 값은 받지 않는다.** 내부 ID, 세션 토큰, 현재 사용자 정보처럼 모델이 알 방법이 없는 값을 파라미터로 요구하면 모델은 지어낸다. 그런 값은 도구를 실행하는 내 코드 쪽에서 채운다.

---

### 6. 결과를 어떻게 돌려줄까

도구 정의만큼 중요한데 자주 놓치는 부분이다. 도구가 반환한 결과는 그대로 모델에게 들어간다.

**필요한 것만 돌려준다.** DB에서 조회한 레코드를 컬럼 40개 그대로 넘기면 토큰만 먹고 모델이 중요한 필드를 놓친다. 모델이 판단에 쓸 필드만 골라서 넘긴다.

**에러도 모델이 읽을 수 있게.** 스택 트레이스를 그대로 넘기지 말고 "해당 주문을 찾을 수 없음 (order_id: 12345). 주문 번호를 다시 확인하거나 search_orders로 검색해볼 것"처럼 다음에 뭘 하면 되는지까지 적어준다. 모델은 이 메시지를 읽고 재시도하거나 사용자에게 물어본다.

**빈 결과도 명시한다.** 빈 배열 `[]`만 돌려주면 모델이 "에러인가, 결과가 없는 건가" 헷갈린다. "조건에 맞는 주문이 없음. 기간을 넓히거나 상태 필터를 제거해볼 것"처럼 쓴다.

---

### 7. 도구 개수와 구성

도구가 많을수록 좋은 게 아니다. 수십 개가 넘어가면 모델이 고르는 데 실수가 늘고, 도구 정의 자체가 매 요청의 토큰을 차지한다.

- 비슷한 도구는 합친다. `get_user_by_id`, `get_user_by_email`, `get_user_by_name`보다 `get_user`에 파라미터를 하나 받는 게 낫다.
- 반대로 한 도구가 너무 많은 일을 하면 쪼갠다. `manage_order`에 action 파라미터로 create/update/cancel/delete를 다 넣는 건 모델에게 부작용을 숨기는 꼴이다.
- 현재 작업에 필요 없는 도구는 빼거나 나중에 로드한다. 코드 작업 중이면 캘린더 도구는 안 보여주는 식이다.

---

### 8. 테스트

도구 정의를 바꾸고 나면 "모델이 잘 고르는지"를 확인해야 하는데, 이건 단위 테스트로 못 잡는다. 실용적인 방법은 이렇다.

1. 사용자 요청 10~20개를 미리 적어둔다. 도구를 써야 하는 것, 쓰지 말아야 하는 것, 비슷한 도구 중 하나를 골라야 하는 것을 섞는다.
2. 각 요청에 대해 기대하는 도구와 인자를 적는다.
3. 도구 정의를 바꿀 때마다 돌려서 어긋나는 게 있는지 본다.

모델이 틀리면 모델을 탓하기 전에 설명을 고친다. "이 상황에서 왜 저 도구를 골랐을까"를 모델 입장에서 생각해보면 대개 설명에 그 상황이 빠져 있다.

### 정리

| 요소 | 요령 |
|------|------|
| 이름 | 동사 + 대상, 영역별 접두어 |
| 설명 | 무엇·언제·결과 모양·부작용, 비슷한 도구와의 경계 |
| 파라미터 | 전부 설명 붙이기, enum 활용, 개수 줄이기, 모델이 모르는 값은 받지 않기 |
| 결과 | 필요한 것만, 에러와 빈 결과도 다음 행동이 보이게 |
| 구성 | 비슷한 건 합치고, 부작용이 다른 건 쪼개고, 안 쓰는 건 빼기 |

도구 정의는 모델에게 건네는 API 문서다. 사람이 처음 보는 API 문서를 읽고 바로 쓸 수 있을 정도로 쓰면, 모델도 쓸 수 있다.
