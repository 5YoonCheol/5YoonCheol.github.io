혼자 만드는 사이드 프로젝트는 보통 main 하나에 바로 커밋한다. 처음엔 그게 제일 빠르다. 그런데 사이트가 실제로 배포되어 누군가 보고 있는 순간부터 얘기가 달라진다. 작업 중인 미완성 상태가 그대로 올라가고, 뭔가 깨졌을 때 어디까지가 멀쩡한 상태였는지 찾기 어려워진다. 브랜치 전략은 팀 규모 문제가 아니라 "배포되는 코드와 작업 중인 코드를 구분할 필요가 있는가"의 문제다. 대표적인 전략 몇 가지와 혼자 할 때 어디까지 가져가면 좋은지 정리해보자.

---

### 1. 브랜치 전략이 해결하는 문제

브랜치 전략은 결국 두 질문에 대한 답이다.

- 지금 배포된 코드가 어떤 커밋인지 바로 알 수 있는가?
- 작업 중인 코드가 배포에 섞여 들어가지 않는가?

main에 바로 커밋하면 두 질문 모두 "글쎄"가 된다. 커밋 하나하나가 배포 단위가 되어버리고, 작업을 반쯤 하고 저장한 상태도 배포로 나간다. 이걸 막는 가장 단순한 방법은 "배포되는 브랜치"와 "작업하는 브랜치"를 나누는 것이고, 어떻게 나누느냐에 따라 전략 이름이 달라진다.

---

### 2. Git Flow

가장 오래되고 가장 복잡한 방식이다. 브랜치가 다섯 종류다.

- `main`: 배포된 코드. 태그로 버전을 찍는다.
- `develop`: 다음 배포를 위해 기능이 모이는 곳.
- `feature/*`: 기능 하나를 만드는 브랜치. develop에서 따서 develop으로 머지.
- `release/*`: 배포 직전 준비. develop에서 따서 버그만 고치고 main과 develop 양쪽에 머지.
- `hotfix/*`: 배포된 버전의 급한 수정. main에서 따서 main과 develop 양쪽에 머지.

```text
main     ──●───────────────●──────────●──
            \             / \        /
hotfix       \           /   ●──────●
              \         /
release        \       ●───●
                \     /
develop  ────────●───●───●───●───●──
                  \     /     \ /
feature            ●───●       ●
```

버전을 명시적으로 관리하고, 여러 버전을 동시에 유지해야 하는 소프트웨어(설치형 프로그램, 라이브러리)에 맞다. 반대로 웹 서비스처럼 항상 최신 버전 하나만 배포하는 경우에는 release 브랜치가 할 일이 거의 없어서 과하다. 혼자 하는 프로젝트에 이걸 그대로 가져오면 머지만 하다 하루가 간다.

---

### 3. GitHub Flow

Git Flow의 반대편에 있는 단순한 방식이다. 브랜치가 두 종류다.

- `main`: 항상 배포 가능한 상태.
- 작업 브랜치: main에서 따서 작업하고, PR을 열어 리뷰받고, main에 머지한다. 머지되면 바로 배포.

```text
main     ──●─────●─────●─────●──
            \   /  \   /
작업 브랜치   ●─●    ●─●
```

규칙은 하나다. main에 있는 건 전부 배포 가능해야 한다. 그래서 작업 브랜치에서 PR을 열고, 테스트가 통과하고, 확인이 끝난 다음에만 머지한다. GitHub Pages나 Vercel처럼 main 푸시로 자동 배포되는 환경과 잘 맞는다.

단점은 "머지는 했는데 아직 배포하기 싫은" 상태를 표현할 수 없다는 것이다. 기능 세 개를 모아서 한 번에 내보내고 싶으면 머지를 미루는 수밖에 없고, 그러면 PR이 쌓인다.

---

### 4. 중간 지점: main + develop

Git Flow에서 release와 hotfix를 빼고 develop만 남긴 형태다. 실제로 소규모 팀이나 개인 프로젝트에서 가장 흔하게 보인다.

- `main`: 배포된 코드. main에 푸시되면 자동 배포.
- `develop`: 작업이 모이는 곳. 기능 브랜치는 develop으로 PR.
- 배포하고 싶을 때 develop에서 main으로 PR을 열어 머지.

```text
main     ──●───────────●───────────●──
            \         /             /
develop  ────●───●───●───●───●─────●──
              \ /     \ /   \ /
feature        ●       ●     ●
```

이 방식의 장점은 두 가지다.

**배포 단위를 내가 정한다.** 작은 수정 세 개를 develop에 머지해두고, 확인한 다음 한 번에 main으로 올린다. develop → main PR이 곧 배포 기록이 된다. PR 제목에 "배포: 목록 필터와 비교 기능"처럼 적어두면 나중에 언제 뭐가 나갔는지 PR 목록만 봐도 알 수 있다.

**작업 중 상태가 배포에 안 섞인다.** develop에 올려두고 로컬이나 미리보기 환경에서 확인하는 동안 main은 그대로다. 뭔가 잘못됐으면 main으로 올리기 전에 develop에서 고친다.

단점은 머지가 두 번이라는 것이다. 기능 → develop, develop → main. 기능 하나 바꾸고 바로 배포하고 싶을 때는 번거롭다. 그리고 develop과 main이 오래 벌어지면 main으로 올리는 PR이 커져서 뭐가 나가는지 파악하기 어려워진다. develop에 뭔가 쌓이면 가능한 빨리 main으로 보내는 게 요령이다.

---

### 5. 트렁크 기반 개발

main 하나에 모두가 자주(하루에 여러 번) 머지하는 방식이다. 브랜치는 하루 이상 살지 않는다. 미완성 기능은 기능 플래그로 숨기고 코드는 main에 들어간다.

브랜치 전략보다는 팀 운영 방식에 가깝다. 자동 테스트와 배포 파이프라인이 탄탄할 때 가능하고, 혼자 하는 프로젝트에서는 사실상 "main에 바로 커밋"과 구분이 안 된다. 다만 "브랜치를 오래 끌지 말라"는 원칙은 어느 전략을 쓰든 유효하다.

---

### 6. 그래서 혼자 할 때는

조건에 따라 다르다.

**아직 배포 안 했거나, 배포됐어도 나만 본다** → main 하나로 충분하다. 커밋만 잘 나눠두자.

**배포돼 있고 남이 본다, 배포는 자동** → GitHub Flow. 작업 브랜치 + PR + main 머지. 혼자라도 PR을 여는 이유는 머지 전에 diff를 한 번 훑어보게 되기 때문이다. 셀프 리뷰지만 의외로 많이 잡힌다.

**여러 작업을 모아서 한 번에 내보내고 싶다, 또는 배포 전에 확인하는 단계가 필요하다** → main + develop. 특히 AI 코딩 도구를 써서 PR이 여러 개 동시에 열리는 상황이면, 각 PR을 develop에 먼저 모으고 한 번에 main으로 보내는 게 편하다. PR마다 바로 배포되면 중간에 어색한 상태가 사용자에게 노출될 수 있다.

어느 쪽이든 공통으로 지킬 것은 세 가지다.

1. 배포 브랜치(main)에는 직접 커밋하지 않는다. 브랜치 보호 규칙을 켜두면 실수로 푸시하는 걸 막아준다.
2. 작업 브랜치는 짧게 산다. 하루 이틀 안에 머지하고 지운다.
3. 머지 후 브랜치는 삭제한다. GitHub 설정에서 머지 시 자동 삭제를 켜두자.

---

### 7. 브랜치 이름 규칙

전략을 정했으면 이름도 정해두자. 혼자라도 나중에 목록을 봤을 때 뭐 하던 브랜치인지 알아야 한다.

```text
feature/order-filter       기능
fix/login-redirect-loop    버그 수정
chore/update-dependencies  설정, 의존성, 잡일
docs/api-guide             문서
```

접두어 뒤에는 소문자와 하이픈만 쓴다. 이슈 트래커를 쓴다면 `feature/123-order-filter`처럼 번호를 넣어두면 PR과 이슈가 자동으로 연결된다.

---

### 정리

| 전략 | 브랜치 | 맞는 경우 |
|------|--------|----------|
| main 하나 | main | 배포 전, 혼자 보는 프로젝트 |
| GitHub Flow | main + 작업 브랜치 | 자동 배포, 머지 즉시 배포해도 되는 서비스 |
| main + develop | main, develop, 작업 브랜치 | 모아서 배포, 배포 전 확인 단계 필요 |
| Git Flow | 5종 | 버전 관리가 필요한 설치형 소프트웨어, 라이브러리 |

전략은 바꿔도 된다. 처음엔 main 하나로 시작해서 배포가 생기면 작업 브랜치를 따고, 모아서 내보낼 필요가 생기면 develop을 추가하는 식으로 필요할 때 한 단계씩 올리면 된다. 중요한 건 "지금 배포된 게 어떤 코드인지"를 항상 답할 수 있는 상태를 유지하는 것이다.
