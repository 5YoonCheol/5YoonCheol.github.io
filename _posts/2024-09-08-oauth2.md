"구글로 로그인", "카카오로 로그인" 같은 소셜 로그인 버튼 뒤에서 돌아가는 게 OAuth 2.0이다.

OAuth 2.0은 사용자가 비밀번호를 넘겨주지 않아도 애플리케이션이 사용자 데이터에 접근할 수 있게 해주는 표준 인증 프로토콜이다. 사용자, 애플리케이션(클라이언트), 인증 서버, 자원 서버가 서로 주고받으면서 동작하고, 주로 API 접근 권한을 관리하는 데 쓴다.

---

### 등장인물 넷

**Resource Owner (자원 소유자)**
보통은 사용자다. Google Drive 파일이나 Facebook 프로필처럼 자기 자원에 대한 권한을 갖고 있다.

**Client (클라이언트)**
자원 소유자가 접근을 허락한 애플리케이션이나 서비스다. 자원 서버에 사용자 데이터를 달라고 요청하는 쪽이다.

**Authorization Server (인증 서버)**
사용자를 인증하고 클라이언트에게 액세스 토큰을 발급해주는 서버다. Google의 OAuth 서버가 여기에 해당한다.

**Resource Server (자원 서버)**
클라이언트가 원하는 데이터가 실제로 있는 서버다. 인증 서버가 발급한 액세스 토큰을 확인하고 요청을 허락한다. Google Drive 파일이 저장된 서버를 생각하면 된다.

---

### 동작 방식 (Grant Type)

OAuth 2.0은 크게 네 가지 승인 방식으로 동작한다.

#### 1. Authorization Code Grant

제일 많이 쓰는 방식이다. 사용자가 클라이언트에서 인증 서버로 넘어가 로그인을 마치면, 클라이언트는 인증 서버에서 Authorization Code를 받는다. 그리고 이 코드로 다시 액세스 토큰을 요청한다.

액세스 토큰이 사용자 쪽(브라우저)에 직접 노출되지 않아서 보안상 안전하다. 웹 애플리케이션에서 주로 쓴다.

#### 2. Implicit Grant

Authorization Code Grant와 비슷한데, 코드 단계 없이 바로 액세스 토큰을 받는다. 브라우저에서만 돌아가는 SPA(Single Page Application) 같은 곳에서 쓰던 방식이다.

다만 액세스 토큰이 브라우저 URL에 그대로 실려 오기 때문에 보안에 취약할 수 있다.

#### 3. Resource Owner Password Credentials Grant

사용자가 클라이언트에 아이디와 비밀번호를 직접 넣고, 클라이언트가 그걸로 인증 서버에서 액세스 토큰을 받는 방식이다.

비밀번호를 클라이언트에 맡기는 거라 보안성이 낮다. 그래서 믿을 수 있는 내부 시스템이나 일부 모바일 앱처럼 제한된 상황에서만 쓴다.

#### 4. Client Credentials Grant

사용자를 대신하는 게 아니라 클라이언트가 자기 자격 증명으로 직접 액세스 토큰을 받는 방식이다. 서버끼리 통신하거나 백그라운드 작업을 돌릴 때 쓴다.

---

### 액세스 토큰과 리프레시 토큰

- Access Token: 인증 서버가 발급하고, 자원 서버에 접근할 때 쓰는 토큰이다. 일정 시간이 지나면 만료된다.
- Refresh Token: 액세스 토큰이 만료됐을 때 새 액세스 토큰을 받기 위해 쓰는 토큰이다. 액세스 토큰보다 수명이 길다.

---

### 보안은 어떻게 챙기나

- 모든 통신은 HTTPS로 암호화한다.
- 액세스 토큰은 일정 시간이 지나면 만료되고, 리프레시 토큰으로 갱신한다.
- 동의 화면에서 사용자가 클라이언트에 어디까지 허락할지 직접 고른다.

---

### 장점과 단점

애플리케이션마다 사용자 인증 정보를 나눠 줄 필요 없이 데이터 접근을 안전하게 관리할 수 있다는 게 가장 큰 장점이다. 인증 흐름도 여러 가지라 웹, 모바일, 서버 간 통신 등 환경에 맞춰 고를 수 있다.

대신 설정과 구현이 복잡한 편이고, 보안 관련 처리를 제대로 해줘야 한다. 상황에 따라 PKCE 같은 추가 보안 장치가 필요하기도 하다.

---

지금은 웬만한 웹 서비스와 API가 OAuth 2.0을 쓰고 있고, 소셜 로그인에서 특히 자주 볼 수 있다. 사용자는 편하게 로그인하고, 서비스는 비밀번호를 직접 다루지 않아도 되니 양쪽 모두에게 이득인 셈이다.
