> 2026년 11월에 "Blue/Green Deploy"와 "Canary Release" 두 글을 합치고 Rolling 배포와 DB 마이그레이션 절을 더해 다시 썼다. 옛 주소로 들어오면 이 글로 넘어온다.
{: .prompt-info }

서버를 내렸다가 새 버전을 올리는 방식은 그 사이에 서비스가 멈춘다. 무중단 배포는 구 버전과 신 버전이 잠시 같이 떠 있는 상태를 만들어 트래픽을 옮기는 방식인데, "어떻게 같이 띄우고 어떻게 옮기느냐"에 따라 세 가지로 나뉜다. 각각의 동작과 롤백, 비용을 비교해보자.

### 1. Rolling 배포

인스턴스 N대를 한 대(또는 몇 대)씩 차례로 새 버전으로 바꾼다. 로드 밸런서에서 한 대를 빼고, 새 버전을 올리고, 헬스 체크를 통과하면 다시 넣는 식이다.

```
[v1][v1][v1][v1]  →  [v2][v1][v1][v1]  →  [v2][v2][v1][v1]  →  ...  →  [v2][v2][v2][v2]
```

- 장점: 추가 인프라가 거의 필요 없다. Kubernetes `Deployment`의 기본 전략이고 대부분의 오케스트레이션 도구가 지원한다.
- 단점: 배포 중에 v1과 v2가 동시에 요청을 받는다. API 응답 형식이나 세션 구조가 다르면 사용자가 요청마다 다른 버전을 만난다. 롤백도 같은 과정을 거꾸로 돌려야 해서 느리다.
- 배포 중 가용 용량이 줄어든다. 4대 중 1대씩 바꾸면 그 동안 75%로 버텨야 하니, 피크 시간은 피하거나 `maxSurge`로 한 대를 먼저 더 띄운다.

### 2. Blue/Green 배포

운영 환경을 두 벌 둔다. 지금 서비스 중인 쪽이 Blue, 새 버전을 올리는 쪽이 Green이다. Green에 새 버전을 올려 충분히 확인한 뒤 로드 밸런서(또는 DNS)의 대상을 Blue에서 Green으로 한 번에 바꾼다.

```
LB → [Blue v1][Blue v1]        [Green v2][Green v2]  (검증 중)
LB → [Blue v1][Blue v1]  ───▶  [Green v2][Green v2]  (전환)
```

- 장점: 전환이 순간이라 다운타임이 사실상 없다. 롤백도 대상을 Blue로 되돌리기만 하면 되니 가장 빠르다. 구 버전과 신 버전이 섞여서 요청을 받는 시간도 없다.
- 단점: 환경을 두 벌 유지해야 하니 인프라 비용이 두 배에 가깝다. 클라우드에서는 전환 뒤 Blue를 내려서 비용을 줄이지만, 그러면 빠른 롤백 창이 그만큼 짧아진다.
- DNS로 전환하면 클라이언트 캐시 때문에 전환이 느리고 고르지 않다. 로드 밸런서의 대상 그룹을 바꾸는 쪽이 낫다.

### 3. Canary 배포

새 버전을 일부 사용자에게만 먼저 내보내고, 지표에 이상이 없으면 비율을 늘린다. 이름은 탄광에서 유독 가스를 먼저 감지하던 카나리아에서 왔다.

```
LB → 95% [v1][v1][v1]   5% [v2]        (관찰)
LB → 50% [v1][v1]      50% [v2][v2]    (확대)
LB → 100% [v2][v2][v2][v2]             (완료)
```

- 장점: 문제가 생겨도 영향 범위가 그 비율의 사용자로 끝난다. 실제 트래픽으로 검증하니 스테이징에서 못 잡는 문제(실데이터, 실제 부하)를 잡을 수 있다. 추가 인프라는 카나리 인스턴스 몇 대뿐이다.
- 단점: "이상이 없다"를 판단할 지표와 도구가 있어야 한다. 에러율, 지연 시간, 비즈니스 지표를 버전별로 나눠 볼 수 없으면 카나리는 의미가 없다. 단계마다 관찰 시간이 필요해서 배포가 오래 걸린다.
- 어떤 사용자를 카나리로 보낼지도 정해야 한다. 무작위 비율이 기본이고, 내부 직원이나 특정 지역을 먼저 보내기도 한다. 같은 사용자가 요청마다 다른 버전을 만나지 않게 세션이나 사용자 ID 기준으로 고정(sticky)하는 게 보통이다.

### 4. 한눈에 비교

| | Rolling | Blue/Green | Canary |
|---|---|---|---|
| 추가 인프라 | 거의 없음 | 환경 한 벌 더 | 소수 인스턴스 |
| 롤백 속도 | 느림 (역순 배포) | 가장 빠름 (대상 전환) | 빠름 (비율 0%) |
| 버전 혼재 시간 | 배포 내내 | 없음 | 의도적으로 길게 |
| 실트래픽 검증 | 없음 | 전환 전 불가 | 핵심 |
| 필요한 것 | 헬스 체크 | 트래픽 전환 장치 | 버전별 지표, 가중치 라우팅 |
| 맞는 상황 | 내부 서비스, 변경이 작을 때 | 롤백이 가장 중요할 때 | 사용자 많고 영향 범위를 줄여야 할 때 |

실제로는 섞어 쓴다. Blue/Green으로 환경을 준비한 뒤 Green에 트래픽을 5%부터 서서히 올리면 둘의 장점을 합친 모양이 된다. Kubernetes에서는 Argo Rollouts, Flagger 같은 도구가 이런 단계적 전환을 자동화한다.

### 5. 어떤 전략이든 DB가 발목을 잡는다

세 전략 모두 "구 버전과 신 버전이 같은 DB를 본다"는 순간이 있다. Rolling과 Canary는 당연하고, Blue/Green도 롤백하려면 Blue가 신 버전이 바꾼 스키마로 동작해야 한다. 그래서 스키마 변경은 항상 하위 호환으로 한다.

컬럼 이름을 바꾸는 경우를 예로 들면, 한 번에 `RENAME COLUMN`을 하면 구 버전이 즉시 깨진다. 대신 세 번에 나눈다.

1. 새 컬럼 추가. 애플리케이션은 두 컬럼에 모두 쓰고 옛 컬럼에서 읽는다 (배포 1).
2. 데이터 백필. 애플리케이션이 새 컬럼에서 읽도록 바꾼다 (배포 2).
3. 옛 컬럼 삭제 (배포 3, 롤백 가능성이 사라진 뒤).

이걸 expand-contract(확장 후 축소) 패턴이라고 부른다. 컬럼 삭제, 타입 변경, NOT NULL 추가처럼 구 버전을 깨는 변경은 모두 이 순서를 따른다. 배포 전략을 아무리 잘 골라도 마이그레이션이 비호환이면 무중단이 아니다.

### 6. 정리

처음 무중단 배포를 도입한다면 Rolling으로 시작하는 게 가장 쉽다. 롤백 시간이 문제가 되면 Blue/Green으로, 장애 영향 범위가 문제가 되면 Canary로 간다. 그리고 어느 쪽이든 DB 마이그레이션을 하위 호환으로 쪼개는 습관이 먼저다.
