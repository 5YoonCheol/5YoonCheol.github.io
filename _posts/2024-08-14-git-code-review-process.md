지금 하고 있는 프로젝트에서는 깃 PR로 코드리뷰를 하고 있다.
많은 회사들이 Git으로 코드리뷰를 하는 걸로 알고 있어서 Git을 활용한 코드리뷰에 대해 정리해보려고 한다.

팀이나 그룹마다 상황에 맞는 전략을 짜는 게 가장 중요하다고 생각한다.
이 글은 "이렇게 진행하는 방법도 있다." 정도로 참고하면 좋을 것 같다.

리뷰 프로세스를 살펴보자!

---

#### 1. Pull Request(PR) 활용하기

Git 코드 리뷰의 중심은 Pull Request(PR)다. 기능 개발이나 버그 수정을 끝내고 메인 브랜치에 합치기 전에 팀원들에게 검토를 받는 기능이다. PR에서 변경 사항을 한눈에 보고, 리뷰어가 고칠 부분에 대해 구체적으로 피드백을 남길 수 있다.

- PR은 작게 만든다. 변경 사항이 많을수록 리뷰어가 파악하기 힘들고 피드백도 대충 하게 된다. 기능 단위로 작게 쪼개서 올리자.
- 제목과 설명을 분명하게 쓴다. 제목에는 작업의 핵심을 짧게 담고, 본문에는 왜 바꿨는지, 뭘 바꿨는지, 어디를 특히 봐줬으면 하는지 적는다. 리뷰어 시간도 아끼고 피드백도 더 좋아진다.

---

#### 2. 브랜치 전략 정하기

리뷰를 제대로 하려면 브랜치 전략이 있어야 한다. 보통 Git Flow나 GitHub Flow 같은 전략으로 브랜치를 관리하고, 기능(feature) 브랜치에서 작업을 끝낸 뒤 PR로 메인 브랜치에 합친다.

- 기능별로 브랜치를 나눈다. 여러 기능을 한 브랜치에서 작업하면 리뷰어가 헷갈린다. 기능마다 브랜치를 나눠서 PR 하나가 기능 하나에만 집중하게 하자.
- 리뷰 요청 전에 브랜치를 동기화한다. PR을 만들기 전에 메인 브랜치 내용을 기능 브랜치에 반영해서 충돌을 줄여두면, 리뷰어는 변경 사항에만 집중할 수 있다.

---

#### 3. 자동화 도구 쓰기

자동화 도구를 붙이면 품질은 지키면서 시간은 아낄 수 있다. Git Hooks나 CI/CD 파이프라인으로 코드 스타일 검사와 테스트를 자동으로 돌릴 수 있다.

- Linting 도구로 코드 스타일을 자동 검사한다. PR을 만들 때 자동으로 돌게 해두면 리뷰어가 스타일 문제까지 일일이 볼 필요가 없다.
- 모든 PR에서 테스트가 자동으로 돌게 한다. 리뷰어는 테스트 결과를 보고 기능상 문제가 없는지 확인할 수 있다.

---

#### 4. 리뷰어와 잘 소통하기

코드 리뷰는 코드만 확인하는 게 아니라 팀원끼리 대화하는 과정이기도 하다. 소통이 잘 되면 리뷰 질도 올라가고 리뷰이도 성장한다.

- 피드백은 구체적이고 분명하게 준다. 지적만 하기보다는 어떻게 고치면 좋을지 방향을 같이 제시하자.
- 리뷰어와 리뷰이가 적극적으로 대화하게 한다. 필요하면 직접 얘기하면서 코드 의도를 설명하거나 피드백을 같이 논의한다.

---

#### 5. 리뷰 후 수정 사항 챙기기

리뷰가 끝나면 피드백을 반영해서 코드를 고쳐야 한다. 수정이 제대로 됐는지 확인하고, 다시 봐야 하면 재리뷰를 요청한다.

- PR 안에서 피드백 반영 상태가 보이게 한다. GitHub에서는 피드백에 맞춰 커밋을 추가하면 PR에서 바로 확인할 수 있다.
- 머지 전에 마지막으로 꼼꼼히 본다. 피드백이 다 반영됐는지 확인하고, 문제가 없을 때만 메인 브랜치에 합친다.

---

#### 6. 프로세스는 계속 고친다

리뷰 프로세스는 한 번 정하면 끝이 아니다. 리뷰어와 리뷰이의 의견을 듣고 더 나은 방법을 들이면서 팀에 맞게 계속 조정해야 한다.

- 회고를 한다. 프로젝트나 스프린트가 끝나면 리뷰하면서 생긴 문제와 개선할 점을 얘기해본다.
- 팀 상황에 맞게 조정한다. 팀 경험이 쌓이면 리뷰 과정을 줄이거나 새 도구를 들여서 더 빠르게 할 수도 있다.

---

정리하면 PR을 작고 분명하게 올리고, 자동화할 수 있는 건 자동화하고, 리뷰어와 리뷰이가 편하게 얘기할 수 있게 하는 게 핵심이다. 그리고 그 방식도 팀에 맞게 계속 다듬어 가면 된다.
